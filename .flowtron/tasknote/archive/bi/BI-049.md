### Drift check — two PLAN.md numbers are wrong

| PLAN.md claim | Measured at HEAD | Verdict |
|---|---|---|
| 1164 L | 1164 L (820 code / 284 comment / 60 blank) | ✅ accurate |
| 40-member `UseWorkspace` interface | **42** members | minor drift |
| "2.7x the next-largest non-test source file" | **1.68x** by total lines (`lib/storage.ts`, 694 L); **1.86x** by code lines (820 vs 441) | **material drift** |

The 2.7x figure was the strongest quantitative argument for a split, and it does
not hold. Across 41 non-test source files totalling 7481 L, `useWorkspace.ts` is
15.6% of the tree — the largest file, but not a dramatic outlier: `storage.ts`
(694) and `workspace.ts` (684) sit right behind it.

No archived tasknote carries the claim (it originates in the `/ft-audit-repo`
PLAN filing of 2026-08-30, which wrote no tasknote), so no ⚠️ superseded-claim
pointer is owed.

### Archive skim — the size is a deliberate, repeatedly reaffirmed architecture

Grepped 59 archived tasknotes mentioning `useWorkspace`. The layering decision is
recorded and re-applied continuously from BI-003 to BI-047:

- **BI-003** established the pure/hook split: `lib/workspace.ts` = React-free
  immutable `Session` mutations; `lib/useWorkspace.ts` = the hook binding them to
  React state + persistence.
- **BI-004 / BI-007 / BI-021.2 / BI-024.1 / BI-024.2 / BI-030.2 / BI-032 / BI-046**
  each re-declare the same three/four-layer split in their Pattern Survey — pure
  contract → FSA/`fs` writes → **hook orchestration** → presentational component.
- **BI-022.1** confirmed `storage.ts` ↔ `useWorkspace` is the *single* persistence
  seam; **BI-022.2/.3** put a `PersistenceAdapter` behind it.
- **BI-030.3 / BI-030.4 / BI-031.2** repeatedly place user-facing strings and
  `window.confirm` in the hook by explicit decision ("`useWorkspace` owns
  transient UI state and user-facing strings").
- **BI-045 / BI-047** kept `ImagegenApi` as the sole injected seam and moved live-root
  *ownership* into the hook on purpose.

So the pure logic is **already extracted** (`workspace.ts` 684 L, `storage.ts` 694 L,
plus `roundSelection.ts`, `imagegenUrl.ts`, `imagegenClient.ts`, `generate.ts`,
`persistence.ts`, `ImagegenContext.tsx`). What remains in `useWorkspace.ts` is the
orchestration residue: React state + `commit` + error strings + effect wiring.
Its size is the *consequence* of the split, not evidence the split never happened.

### Coupling analysis — 26 of 33 functions share one hub

Mapped every function in the hook body to its closure dependencies:

- **Hub:** `session` / `sessionRef`, `commit()`, `setError()`. 26 of the 33
  in-hook functions touch at least two of the three; `commit` alone has 17 callers.
- **Secondary shared closure:** `imagegen` (13 callers), `findGeneratedImage`
  (5 callers), `setActiveTaskId` (6), `loadedRound` (4), `syncImagegenLink` (2).
- **Largest members:** `loadRound` (78 L), `generate` (76 L),
  `handleImagegenApprove` (61 L), `handleImagegenUnapprove` (39 L). All four sit
  on the hub.
- **Genuinely detachable:** only the `generationAvailable` probe effect (~20 L,
  zero closure deps) and the four export functions (~61 L, needing `session` +
  `setError` + `imagegen.resolveBlob`).

Any sub-hook split therefore has to thread a `{ session, sessionRef, commit,
setError, imagegen }` core object into each child — replacing one cohesive
closure with 4-5 files bound by a wide, hand-maintained internal contract.

### Consumer shape

`useWorkspace` has exactly **one** call site: `components/Workspace.tsx:42`
(`const ws = useWorkspace(imagegen)`), which destructures `ws.*` ad hoc across
every cluster and threads individual members down as props. A sub-hook split
would still have to re-merge into one `ws` object for that consumer, so the
42-member surface survives the split unchanged — the decomposition would buy
file granularity, not a narrower public surface.

### Test shape

`lib/useWorkspace.test.ts` (1106 L, 13 `describe` blocks) is already organised
along behavioural seams (generate, generateAll, generationAvailable, import,
unreadable sessions, reversible approve, collision guard, rename guard, delete
retraction, four BI-047 link blocks). A split would require re-homing these and
rebuilding the render harness per sub-hook.

### Clarifying question

The survey's finding is unambiguous, but the *deliverable* it implies is the
operator's call — asked via AskUserQuestion (see Implementation Notes).

**Recommendation: keep it whole.** The one metric that framed it as an outlier
(2.7x) is wrong; the extractable surface is ~80 L of 820; and the split's cost is
a 5-member internal core contract threaded through 4-5 files to serve a single
consumer that re-merges them anyway.
