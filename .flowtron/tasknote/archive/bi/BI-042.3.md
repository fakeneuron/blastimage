# BI-042.3 | consumer-recovery-test

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-042]] · [[BI-042.2]]

## 🎯 Goal

Pin BI-042.2's fix at the consumer level: a mounted `ResolvedImage` on an `imagegen:` URL must end up on a **live** blob URL after a same-round reload and after LRU eviction pressure — the contract `lib/ImagegenContext.test.tsx` never reaches because it drives the provider through `renderHook`, not a rendered `<img>`.

## ✅ Acceptance

- [x] `components/ResolvedImage.test.tsx` pins **same-round reload recovery**: a mounted `imagegen:rounds/r1/…` image whose blob URL is revoked by `readRound(1)` re-resolves and ends on a *different*, un-revoked blob URL.
- [x] It pins **eviction survival**: with the mounted image's entry at the oldest end of a full cache, driving past `BLOB_CACHE_MAX_ENTRIES` more resolves never revokes the URL the image is displaying.
- [x] It pins **no raw-URL flash on an unrelated round**: an r2 image mounted across a `readRound(1)` bump stays on its live blob URL and never renders its raw `imagegen:` src (the contract BI-042.2's split `[src]` effect exists for, currently untested).
- [x] "Live" is asserted structurally, not by string equality — the `URL` stub tracks created-minus-revoked blob URLs, and re-minting a path yields a distinct string so a re-resolve is observable.
- [x] Every new assertion is mutation-checked: removing `blobEpoch` from the resolve deps fails (1); removing the retain effect fails (2); merging the `[src]` reset back into the resolve effect fails (3).
- [x] The existing `ResolvedImage` and `ImagegenContext` contracts still pass unchanged; no production `.ts`/`.tsx` file is modified.
- [x] `npm test`, `npm run lint`, `npx tsc --noEmit` all clean.

**Discovery Notes:**

**What is actually untested today.** BI-042.2's two revocation paths each got provider-level coverage, but both consumer contracts are inferred, not asserted:

| Path | Provider-level test (exists) | Consumer-level contract (missing) |
|---|---|---|
| `invalidateRoundBlobs` (staleness) | `blobEpoch` bumps on `readRound(1)`, not on `readRound(2)` | a mounted `<img>` actually re-resolves onto new bytes |
| `evictOldestBlob` (memory bound) | held entries are skipped; the bound goes soft | a mounted `<img>` is what does the holding |

The second row is the sharper gap: `retainDisplayUrl` is only ever called by hand in the existing tests, so the wiring that matters in production — `ResolvedImage`'s retain effect, and its `displaySrc` dep — is unexercised. Delete that effect today and the whole suite stays green.

**Why the `URL` stub has to change.** `stubBlobUrls` mints `blob:${(obj as File).name}`, and the FS mock names every file after its path — so `blob:rounds/r1/hero.png` is minted, revoked, and minted again as the *same string*. Under that stub, "the image recovered from a revocation" and "the image never noticed" are indistinguishable. Minting `blob:<path>#2` on the second sight of a path makes the re-resolve observable, and a `live` set (add on create, delete on revoke) turns "stays live" into a real assertion. First-mint strings are unchanged, so the five existing exact-string assertions are untouched.

**Why test (3) needs a synchronous `act`.** The raw-URL flash it guards against is transient: if the `setDisplaySrc(src)` reset were merged back into the resolve effect, the image would show its raw src only between the effect flush and the resolve microtask. `await act(async () => {})` drains both and hides it. But `readRound`'s `setBlobEpoch` runs synchronously before its first `await`, so `act(() => { void api.readRound(1) })` flushes the bump and re-runs the effects with the resolve still pending — the one moment where the flash is observable. An r2 image is the right subject: its entry was not invalidated, so its blob URL is still live and *should not* change at all.

**Phase 1→2 judgment:** Discovery surfaced no significant scope deviation — same file, same mechanism, no approach change; the one added test and the `stubBlobUrls` extension are both inside the filed scope → skip 🛠️.
