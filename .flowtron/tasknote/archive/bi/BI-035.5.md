# BI-035.5 | lightbox-focus-management

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-035]] [[TEST-002.4]] [[BI-027]]

## 🎯 Goal

Make `components/Lightbox.tsx` honour the modality it already declares — move focus
into the overlay on open, keep Tab inside it while open, and restore focus to the
triggering thumbnail on close.

## ✅ Acceptance

- [x] Opening the lightbox moves focus into the overlay (no longer left on the
      thumbnail behind the backdrop)
- [x] Tab / Shift+Tab cycle within the overlay's controls; focus cannot reach the
      page behind an `aria-modal="true"` overlay
- [x] Closing the lightbox (Escape, Close button, or backdrop click) restores focus
      to the element that had it before the overlay opened
- [x] The element carrying `role="dialog" aria-modal="true"` actually contains the
      overlay's own controls (see the boundary finding in Discovery)
- [x] Existing `Lightbox` behaviour is unchanged: arrow/button stepping and its
      clamps, Escape/backdrop close, the `multiple` gate, and listener teardown
- [x] `components/Lightbox.test.tsx` extended with focus coverage; any pinned
      assertion that this task deliberately changes is updated with a stated reason
- [x] `npm test`, `npm run lint`, `npm run typecheck` green

**Boundary finding — the dialog element does not contain its own controls.**

The overlay's DOM is a backdrop `<div>` with four children: Close, Previous,
`<figure role="dialog" aria-modal="true" aria-label="Image viewer">`, Next. The three
buttons are **siblings** of the dialog element, not descendants. This matters because
a focus trap needs a boundary, and today's boundary excludes every control the trap
would cycle between. It is also an independent a11y defect: a screen-reader user
entering "Image viewer, dialog" finds an image and a counter, with Close and the nav
buttons outside the modal container they belong to.

Layout note that makes the fix cheap: all three buttons are `absolute`, and `<figure>`
carries no `relative`, so their positioning anchor is the `fixed` backdrop either way
— moving them inside the figure is a DOM-parent change with **no visual change**.

**Sibling-pattern note.** `FeedbackModal`, `IterateModal`, and `DeleteTaskModal` all
declare `aria-modal="true"` and manage focus with a single `autoFocus` on a natural
first control — no trap, no restore. So there is no established trap pattern in this
codebase to extend; this task introduces the first one. It stays inside `Lightbox`
(see Best Practices Review) and does not retrofit the siblings.

## 🛠️ Phase 2: Execution

- [x] **Pattern survey** — no trap pattern existed to extend: all three sibling modals
  declare `aria-modal="true"` and manage focus with a lone `autoFocus`, so this is the
  codebase's first. The **new shape is justified** rather than borrowed, and kept as
  small as the job allows — the trap rides the component's *existing* `window` keydown
  effect as one more `else if` branch beside Escape/Arrow, so the overlay still has a
  single keyboard entry point rather than two competing listeners. **Not extracted to a
  shared hook:** three siblings share the gap, so a `useFocusTrap` will eventually have
  four consumers, but building it on first use is the speculative abstraction the
  project standards rule out — and the retrofit is not in a PLAN line that names one
  file. Kept in the component rather than in `lib/`: the old *"pure logic lives in
  `lib/`"* convention existed because components were untestable by config (TEST-001.2
  retired that), and this logic is DOM-bound, so `lib/` would buy an awkward seam and no
  extra coverage. SRP holds — `Lightbox` already owns its own keyboard behaviour.

- [x] **Minimal refactor gate** — one structural change, load-bearing for Acceptance:
  the three controls moved inside the `<figure role="dialog">`. A trap needs a boundary
  and the ARIA boundary excluded every control it would cycle, so this was not optional
  polish. Two things **deliberately left alone**: (1) the nav buttons keep their own
  `e.stopPropagation()`, now redundant against the figure's — they still execute and
  keep each button's non-closing behaviour independent of an ancestor handler, so
  removing them would trade a live guarantee for a one-line diff; (2) the sibling
  modals' identical focus gap is **deferred**, not fixed here.

**Implementation Notes:**

`components/Lightbox.tsx` — +46 lines net, three changes:

| Change | Detail |
|---|---|
| **DOM boundary** | Close / Previous / Next moved inside `<figure role="dialog">`, source order preserved (Close, Previous, image, Next). Visually inert: all three are `absolute` and the figure carries no `relative`, so the `fixed` backdrop stays their positioning anchor. A comment at the move records *why*, so it doesn't read as gratuitous nesting. |
| **Open + restore** | A mount-only effect captures `document.activeElement`, focuses the dialog (`ref` + `tabIndex={-1}` + `focus:outline-none`, so no stray ring on a programmatic focus), and restores the opener in cleanup. Both consumers unmount on close, so one mechanism covers Escape, Close, and backdrop alike. |
| **Managed Tab** | A `Tab` branch on the existing `window` keydown effect. Collects `FOCUSABLE` descendants of the dialog, finds the active one, and moves to the neighbour, wrapping at both ends; `at === -1` (focus on the dialog itself) enters at the first or last control by direction. Returns without `preventDefault()` when the dialog isn't rendered, so an empty set doesn't swallow Tab for the page behind. |

**Side effect, previewed and accepted at the Discovery ask:** with Close inside the
figure, the figure's `stopPropagation` now covers it, so `onClose` fires **once**
instead of twice. TEST-002.4 left a pin on that quirk *"so that adding the missing
`stopPropagation` shows up here as a deliberate change instead of passing silently"* —
it fired on the first run, exactly as designed, and is now rewritten to assert `1` with
a docstring recording what changed and why.

`components/Lightbox.test.tsx` — +10 tests (23 → 33). New `focus management (BI-035.5)`
describe: initial focus, restore-to-opener, first-Tab entry, forward cycle + end wrap,
backward entry, backward wrap, disabled-button skip, single-image hold, `preventDefault`
while trapping, and stand-down when no dialog renders. The file header's "focus
behaviour is deliberately absent" paragraph was rewritten — leaving it would have been
the stale code-facing doc Phase 3 asks about.

Two assertions were **added after a first mutation pass showed two branches unprovable**
(the empty-target guard and `preventDefault` are both invisible to focus assertions,
since happy-dom implements no sequential focus navigation): both now assert on
`fireEvent`'s dispatch result, which is `false` once `preventDefault` has run.

**Final Summary:**

`components/Lightbox.tsx` declared `role="dialog" aria-modal="true"` from BI-027 onward
while enforcing none of it. It now does: opening moves focus to the dialog, Tab and
Shift+Tab cycle its own controls in both directions with wraps at both ends, and closing
hands focus back to the thumbnail that opened it.

**Changed:** `components/Lightbox.tsx` (+46 net) and `components/Lightbox.test.tsx`
(23 → 33 tests), plus one `.flowtron/PLAN.md` line. No dependency added — no focus-trap
library; the dialog holds only buttons.

**The structural fix under the feature.** A trap needs a boundary, and the boundary was
wrong: Close / Previous / Next were *siblings* of the `<figure role="dialog">`, not
descendants, so the element claiming modality contained an image and a counter while its
controls sat outside. Moving them inside is what makes both the trap and the ARIA
boundary honest. Visually inert by construction — all three are `absolute` and the figure
carries no `relative`, so the `fixed` backdrop stays their anchor — and the operator
confirmed that in the running app, which is the one claim no assertion could check.

**Verification:** `npm test` 372 → **382 passed** / 25 files; lint and `tsc --noEmit`
clean. The load-bearing check is the mutation pass: seven new focus branches broken in
turn, every one failing on exactly the test written for it, file restored and `diff -q`
verified identical afterwards. A *first* mutation pass found two branches unprovable —
the empty-target guard and `preventDefault()` are invisible to focus assertions because
happy-dom implements no sequential focus navigation — so two assertions were added on
`fireEvent`'s dispatch result before the pass was rerun. The 22 pre-existing behavioural
tests passed untouched throughout, which is the evidence the DOM move changed the
boundary without changing behaviour.

**A pinned quirk collected, as designed.** TEST-002.4 had pinned `onClose` firing
**twice** from Close — the button carried no `stopPropagation`, so its click also reached
the backdrop — explicitly *"so that adding the missing `stopPropagation` shows up here as
a deliberate change instead of passing silently."* Moving Close inside the figure put it
under the figure's existing `stopPropagation`, the pin failed on the first run, and it is
now rewritten to assert `1` with a docstring recording what changed. The tripwire worked
exactly as intended.

**Refactors:** one made, load-bearing (the DOM move above). Three deferred with reasons:
no `useFocusTrap` extraction (four eventual consumers, but building a shared hook on its
first use is speculative); the nav buttons keep their now-redundant `stopPropagation`
(they still execute, and dropping them would make each button's non-closing behaviour
depend entirely on an ancestor); and the three sibling modals' identical gap is left for
`BI-035.N` to triage.

**Docs:** all four AI-referenced docs swept — three unchanged with reasons, `PLAN.md`
updated. Code-facing docs were updated rather than left stale: the component docstring
gained a focus contract, and the test file's header paragraph asserting focus behaviour
was *"deliberately absent"* was rewritten, since it had just become false.

**Maintainability:** the defect this closes was invisible in use — the keydown handler is
bound to `window`, so arrows and Escape work regardless of where focus sits, and the
overlay looks perfectly operable while a keyboard user Tabs straight through it into the
live page behind. That class of bug does not announce itself, so it is now pinned by ten
tests, each proven live by mutation. The epic's founding assumption that modals were
already accessible is recorded above as false, with the evidence, for the audit child.
