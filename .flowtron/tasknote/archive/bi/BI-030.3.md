# BI-030.3 | rename-slug-guard

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-030]]

## 🎯 Goal

Warn the user when renaming a task changes its slug and thereby breaks the `slugify(name)` join to a terminal round already on disk — instead of silently orphaning the task.

## ✅ Acceptance

- [x] Renaming a task that carries `imagegen:rounds/r<N>/…` images, where `slugify(newName) !== slugify(oldName)`, raises a confirm naming the current disk slug, the new slug, and the affected round number(s)
- [x] Cancelling the confirm leaves the task name unchanged in session state **and** restores the TaskDetail name field to the stored name (no field/state divergence)
- [x] A slug-preserving rename (`Hero Banner` → `hero banner!`) never prompts
- [x] A task with no on-disk round images never prompts
- [x] The check reads session state only — `imagegen.linked` is never consulted, so a rename made before re-linking still warns
- [x] Both rename entry points (Sidebar `window.prompt`, TaskDetail blur) pass through the guard via the single `useWorkspace.renameTask` choke point
- [x] Tests cover the pure predicate (`workspace.test.ts`) and the hook's confirm orchestration (`useWorkspace.test.ts`, real `confirm` seam via `vi.stubGlobal`)
- [x] `npm test`, `npx tsc --noEmit`, `npm run lint` all clean

**Discovery Notes:**

**Why the join breaks (mechanism).** The disk side of the slug never comes from app state. `/blast-generate` computes `slug = slugify(name)` from `imagegen/tasks.json` (SKILL.md §1), and `/blast-iterate` carries slugs forward from the prior `batch.json` (§4). The host repo owns `tasks.json` (`docs/REVIEW-LOOP.md` §2) and the app never writes it — **⇪ Import** and **🛠 Build** only read/emit. So an in-app rename moves one end of a two-ended join and nothing reconciles it.

**Clarifications (both answered, recommended option taken):**

1. *Warning surface* → **blocking `window.confirm`** before the rename applies. It is the only option that lets the user avoid the breakage rather than read about it afterwards, and it matches `Sidebar.tsx`'s existing `window.prompt`/`window.confirm` idiom. The message names the current disk slug, the new slug, the affected round(s), and the remedy (rename `imagegen/tasks.json` to match, or keep the name).
2. *Unlinked imagegen folder* → **warn anyway**. Detection needs no filesystem access — a task carrying `imagegen:rounds/…` image URLs is evidence enough — and the round files exist on disk whether or not this browser session has re-linked the folder. This deliberately diverges from `BI-030.2`'s "silent no-op when unlinked" for the approve-clear, because that path needed an FS handle to do its work and this one does not; suppressing here would leave the pre-relink rename silently broken, which is the exact failure this task closes.

**Detection rule.** Slug-vs-slug, not name-vs-name: `slugify(oldName) !== slugify(newName)` **and** the task has ≥1 image whose URL parses to a round number. Comparing slugs is what keeps cosmetic renames (`Hero Banner` → `hero banner!`) silent. Scope is any round the task's images came from, not just `loadedRound` — a task last seen in r1 while r2 is loaded is equally orphaned on disk.

**TaskDetail divergence hazard (found in Discovery, in scope).** `TaskDetail.tsx:81–90` is an *uncontrolled* input (`defaultValue` + `key={task.id}`). On Cancel, session state keeps the old name but the field keeps showing the typed one, and nothing re-renders it — a silent state/UI divergence, which would be an ironic thing for this epic to ship. Fix: `useWorkspace.renameTask` returns whether it applied, and the blur handler resets the input on decline. The imperative one-line reset is chosen over converting to a controlled `nameDraft` (the `promptDraft` shape): the field's uncontrolled design is deliberate (`CORE-001.3`), and the reset is strictly less machinery for the same result. The Sidebar path needs no equivalent — its `window.prompt` closes and the list re-renders from session state.

**Explicit assumptions:** (1) scope is rename-time warning only — no persistent "orphaned" chip on the task, and no attempt to keep `tasks.json` in sync (that would re-architect the join, which the epic forbids); (2) `deleteTask` breaks the same join and is deliberately out of scope for this task; (3) the `renameTask` return-type widening (`void` → `boolean`) is the minimum public-surface change Acceptance requires, and `Sidebar`'s `(id, name) => void` prop accepts it unchanged.

Discovery surfaced no significant deviation → skip 🛠️.

**Implementation Notes:**

Four source files, ~60 LOC. `renameSlugBreak` returns the whole message payload (`currentSlug` / `nextSlug` / `rounds`) rather than a bare boolean, so the hook composes the warning without a second traversal. Rounds are deduped and sorted so a task carrying images from r3 and r10 reads `r3, r10`, not insertion order.

Two decisions worth naming. **Slug-vs-slug, not name-vs-name:** the guard compares `slugify(old)` to `slugify(new)`, so cosmetic renames (`Hero Banner` → `hero banner!`) stay silent — comparing names would have made the warning noisy enough to train the user to click through it. **`imagegen.linked` is deliberately not consulted:** detection is pure session state (a task carrying `imagegen:rounds/…` URLs), and the round files exist on disk regardless of whether this browser session has re-linked the folder. This diverges from [[BI-030.2]]'s "silent no-op when unlinked" for the approve-clear — that path needed an FS handle to do its work; this one does not, and suppressing it would leave the pre-relink rename silently broken.

The `TaskDetail` reset is a one-line imperative `e.target.value = task.name` rather than a controlled `nameDraft`. The field's uncontrolled `defaultValue` + `key={task.id}` design is deliberate (CORE-001.3) and the reset is strictly less machinery than adding state + a resync effect for the same result.

Renaming a task no longer silently orphans it from the round files on disk: when a rename would change `slugify(name)` for a task that carries round images, the app now raises a blocking confirm naming the stale disk slug, the new slug, and the affected rounds, and declining leaves both the session and the name field untouched.
