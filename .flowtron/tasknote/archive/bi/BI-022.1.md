## 🧭 Deep Pre-pass

### Constitution

**Principles & non-negotiables:**

1. **Hosted is a variation, not a replacement.** The current local, frontend-only, localStorage, submodule-adoptable mode stays fully supported and remains the default. Hosted is an additive deployment target — no regression for local/adopter users.
2. **Reuse the core domain model.** `lib/types.ts` (Session/Task/Iteration/GeneratedImage) and the pure `lib/workspace.ts` transforms are the shared core. Hosted mode swaps the *persistence + auth* layer beneath them, not the domain logic.
3. **Persistence behind a seam.** Today `lib/storage.ts` + `useWorkspace` bind directly to localStorage. Hosted mode introduces a storage-adapter boundary so the same UI/hook drives either localStorage or a cloud backend.
4. **Backend = Supabase** (auth + hosted Postgres + RLS + storage buckets) unless Discovery surfaces a reason otherwise — the standard stack for auth/hosted-Postgres/RLS needs.
5. **Auth-gated, owner-scoped data; RLS as defense-in-depth.** Personal-use (single operator), so multi-tenant leakage isn't the threat — but rows stay owner-scoped with RLS applied as good practice, leaving room to widen later without a rewrite.
6. **Images → blob storage.** localStorage data URLs don't scale to a cloud DB; generated + reference images land in object storage, the DB holds references + provenance.

**Explicit non-goals (this epic):**

- **Not a public multi-tenant SaaS** — this is a single-operator, personal-use hosted instance (auth gates *your* access across devices). Widening to multiple users is a later epic if ever.
- Not team/collaboration (shared workspaces, real-time co-editing).
- Not abandoning Grok Build — generation keeps riding Grok Build (CLI auth, frontend on top), not a new BYO-key or operator-shared-key API path.
- Not billing/payments/quota enforcement.

_(Generation-path / migration / auth / hosting questions resolved in §Clarifications below.)_

### Specification

**Epic scope (WHAT):** a Supabase-backed, **personal-use** (single-operator) hosted deployment of blastimage that coexists with the local mode — sharing the domain core (`lib/types.ts` + `lib/workspace.ts`), swapping persistence + auth beneath a seam, keeping generation on Grok Build (CLI auth + frontend on top), and deploying to Cloudflare Pages.

**Anticipated implementation children (provisional, N=6 → .2–.5):**

**BI-022.2 — storage-adapter seam** (enabling refactor, no backend)
- *Deliverable:* extract a `PersistenceAdapter` interface from today's `lib/storage.ts`; localStorage becomes the default adapter; `useWorkspace` depends on the interface, not localStorage directly.
- *Acceptance:* local mode behaves identically (existing suite green); the adapter boundary is the single seam the cloud backend later implements; no UI change.
- *Interactions:* foundation for .3/.4; must land first.

**BI-022.3 — Supabase auth + schema + RLS**
- *Deliverable:* Supabase project config; **OAuth (Google/GitHub)** login/session; Postgres schema mirroring the domain model (sessions/tasks/iterations/image-metadata) with owner-scoped RLS; a Supabase adapter implementing the .2 seam for metadata.
- *Acceptance:* the logged-in operator's workspace metadata round-trips to Postgres; RLS scopes rows to the owner; local mode unaffected (adapter is config-gated).
- *Interactions:* consumes .2's seam; precedes .4 (schema holds image references).

**BI-022.4 — image blob storage + migration**
- *Deliverable:* generated + reference images to Supabase storage buckets (replacing localStorage data URLs in hosted mode); DB rows reference bucket objects; an importer migrating an existing local session into a cloud account via the existing export/backup surfaces.
- *Acceptance:* images persist to buckets + render via URLs; provenance manifest still builds; a local session imports cleanly into the cloud account.
- *Interactions:* depends on .3 schema; reuses BI-008/BI-002/BI-019 export/import as the migration on-ramp.

**BI-022.5 — Grok-Build generation in hosted mode + Cloudflare deploy**
- *Deliverable:* preserve the Grok Build generation capability in the hosted deploy — wire the frontend on top of the Grok Build CLI auth so the `__grokImagineProvider` seam still resolves in the Cloudflare-hosted context (precise wiring may need a short spike); plus the **Cloudflare Pages** (next-on-Cloudflare) + Supabase deploy/config story.
- *Acceptance:* the operator generates a batch end-to-end from the hosted instance; deploy reproducible from docs/config; local provider bridge unchanged.
- *Interactions:* needs .3 auth for the per-account session; independent of .4.

**N note:** .3 and .4 are each substantial; .5's generation wiring is the least-defined (Grok Build CLI ↔ hosted frontend) and may itself want a spike or a split. If any child proves too large at implementation time, insert a child and bump the audit from .6.

### Clarifications

| Question | Resolution | Effect on scope |
|---|---|---|
| Hosted-mode generation path | **Personal use only** — generation via the auth available through the **Grok Build CLI**, with the hosted frontend built on top (not BYO xAI key, not an operator-shared key). | Reframes the epic from "multi-user SaaS" → a **personal, cloud-persistent** blastimage. Generation keeps riding Grok Build rather than a new API-key path; the hosted work centers on persistence + auth + deploy. Precise generation wiring resolved in `.5` (may warrant a spike). |
| localStorage → cloud migration | **In-app importer** — reuse the existing session-backup/export surfaces (BI-002/BI-008/BI-019) as the on-ramp. | `.4` builds an upload-a-local-export → lands-in-account importer. |

| Hosting / deploy target | **Cloudflare Pages** (Next.js on Cloudflare) + Supabase as the backend (auth/Postgres/storage). | `.5` deploy = next-on-Cloudflare-Pages; the Cloudflare ↔ Supabase pairing (edge-runtime constraints, env/secret wiring) resolved there. |

**Reframe captured:** "multi-user, accounts" (original PLAN line) narrows to a **single-operator, personal-use hosted instance** — auth gates *your* access across devices and backs cloud persistence; it is **not** a public multi-tenant product. Constitution + Specification above updated to match (non-goal added; RLS demoted to defense-in-depth; generation open-item resolved). The parent epic description will be refined to this framing at `.1` closure.
