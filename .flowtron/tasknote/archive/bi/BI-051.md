# BI-051 | focusable-tabindex-gap

[← PLAN.md](../PLAN.md) · ✅ Completed · 🔗 [[TEST-005]]

## 🎯 Goal

Make `FOCUSABLE` (`lib/useFocusTrap.ts`) honour its own doc comment by excluding
`tabIndex={-1}` `button` and `[href]` elements from the Tab cycle, matching the
guard the `input`/`select`/`textarea` clauses already carry.

## ✅ Acceptance

- [x] `FOCUSABLE` excludes `tabIndex={-1}` on **every** clause, `button` and `[href]` included, so the selector matches its own doc comment ("Disabled controls and explicit `tabIndex={-1}` opt out")
- [x] The `:not([tabindex="-1"])` guard is written once and derived across clauses, so a future clause cannot silently omit it (operator-chosen shape, Discovery ask)
- [x] `lib/useFocusTrap.test.tsx` covers the newly-excluded shapes — a `tabIndex={-1}` button and a `tabIndex={-1}` `[href]` are both skipped by the Tab cycle
- [x] TEST-005's inline comment documenting the gap (test file, ~L42-44) is updated — it now describes a closed contract, not a known hole
- [x] No live consumer's focus behaviour changes; the five existing modal/Lightbox test files stay green
- [x] `npm test`, `npx tsc --noEmit`, `npm run lint` all clean

**Discovery Notes:**

**The defect, precisely.** `FOCUSABLE` is a six-clause selector. Four clauses
(`input`, `select`, `textarea`, and the `[tabindex]` catch-all) carry
`:not([tabindex="-1"])`; two (`button:not([disabled])` and `[href]`) do not.
So a `tabIndex={-1}` button or link inside a dialog remains a Tab stop, while
the module docstring 5 lines above asserts that "explicit `tabIndex={-1}` opt
out". Doc/implementation mismatch, latent — not a live regression.

**"No live consumer affected" — verified, not assumed.** Every `tabIndex={-1}`
in `lib`/`components`/`app` is one of two shapes, both already excluded by the
*current* selector:

| Site | Element | Excluded today by |
|---|---|---|
| Lightbox, Feedback, Iterate, Delete, ImportBuilder, ImagegenLink — dialog containers | `<div role="dialog" tabIndex={-1}>` | `[tabindex]:not([tabindex="-1"])` |
| `ImportBuilder.tsx:158` — hidden `.txt` picker | `<input type="file" tabIndex={-1}>` | `input:…:not([tabindex="-1"])` |

No `<button tabIndex={-1}>` and no `<a href tabIndex={-1}>` exists in the app,
which is exactly why the gap survived BI-039's review and five consumers'
component tests. The fix is therefore behaviour-preserving at HEAD and its
value is forward-looking: the next author who writes a `tabIndex={-1}` button
gets the contract the docstring already promises.

**Implementation Notes:**

**`lib/useFocusTrap.ts`** — `FOCUSABLE` becomes a derived selector. The six base
clauses are listed without the guard; `NOT_OPTED_OUT` is appended to each via
`.map()` and joined. Emitted string is byte-identical to the old one except that
`button:not([disabled])` and `[href]` now carry the suffix — nothing else about
the selector, its ordering, or its two consumers moved. The docstring gains a
paragraph recording *why* it is derived (so a future author doesn't flatten it
back to a literal and reintroduce the gap).

**`lib/useFocusTrap.test.tsx`** — harness gains `<button tabIndex={-1}>` and
`<a href tabIndex={-1}>` alongside the existing disabled button and inert input,
grouping all four opt-out shapes into one run between `second` and `third`.
TEST-005's stale comment (which described the gap as open) is replaced by one
describing the closed contract. Two assertions cover it:

1. The existing cycle test, renamed — one Tab from `second` still lands on
   `third`, now hopping four skipped nodes instead of two. Behavioural proof
   through the real handler.
2. A new direct test asserting `querySelectorAll(FOCUSABLE)` returns exactly
   the three live buttons. Pins the selector itself, so a regression is
   attributed to `FOCUSABLE` rather than to the Tab arithmetic.
