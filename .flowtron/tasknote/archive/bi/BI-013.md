**Discovery Notes:**

- Server already up on 3003 → live test can attach immediately (playwright MCP will be used for UI driving + state injection where needed to deliver real image bytes into the browser context).
- The generate seam is the *only* missing piece for a faithful "real" run; everything downstream (decision model, feedback+useAsReference, iterate primaryRef carry, gallery derivation, export manifest, persistence, review visuals) is production-complete.
- Reference resolution gap already visible in code: `primaryRefImageId` in an iterate can be a *GeneratedImage* id (from a prior keeper), not just a library RefImage id. The simple "lookup in refLibrary" in the GROK-AGENT example must be extended to also scan the task's iterations for the keeper's .url. This will be implemented as part of the caller update.
- Data URL strategy: real generations from the agent tools will be turned into `data:image/...;base64,...` strings (via terminal base64 after image_gen produces a filesystem path) so they are self-contained, persist in localStorage exactly like uploaded refs, and render directly in <img src>.
- Aspect: UI cards are aspect-[3/2] (landscape); image_gen calls should request compatible ratio (e.g. "3:2" or "16:9" or auto with prompt guidance for hero/web use).
- Batch distinctness: real image_gen with the same prompt will naturally vary (temperature / sampling); for a "batch of candidates" we may need slight prompt variations ("version 1", lighting notes, crop hints) or multiple independent calls. Gap to observe and log.
- Quota / perf: each real image is a full base64 (~hundreds of KB) stored in localStorage per iteration. Multiple rounds + refs will grow the blob quickly; 2 MB per-ref cap already exists in ReferenceLibrary — similar pressure will apply to generated results. Surface as gap if observed.

The `__grokImagineProvider` bridge we added is the minimal working integration for an *agent-orchestrated* run; a production host would need to inject the privileged API so a plain `generateBatch` body "just works" without the test shim.

4. **Batch distinctness strategy is call-time variation** — For identical prompt we emitted 4 separate `image_gen` calls (model sampling gave natural differences). No "n" or "variations" batch param was used/exposed on the tool. Real API may differ.
5. **localStorage / data URL bloat** — Every real generation becomes a full base64 data URL (or served asset) persisted exactly like refs. Multiple rounds + tasks + gallery will grow the blob fast. The existing 2 MB *per-ref* guard in ReferenceLibrary does not cover generated results. Quota / perf cliff is now real rather than theoretical.
6. **Generated asset delivery to browser** — The tool returns FS paths under the agent's session folder. For `<img src>` in the running app (and for gallery downloads) they would need copying to a publicly served location (e.g. public/ during the test) or on-the-fly conversion to data: URLs inside the provider. We recorded the paths as the canonical artifacts for this run.

8. **Test surface vs. real non-determinism** — The generate tests continue to assert cross-run determinism and specific URL shapes only because a *test* provider reproduces the old mock. Real provider runs (the point of BI-013) are intentionally non-deterministic. This is expected; the contract tests (count, prompt passthrough, batchSize) are what matter for the seam.
