# BI-047 | imagegen-project-binding

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-046]] · [[BI-045]]

## 🎯 Goal

Bind each project to its own `imagegen/` root so switching project re-links the folder automatically, a round can only ever be ingested into the project that owns it, and the sidebar names the folder it is bound to.

## ✅ Acceptance

- [x] A project (`Session`) carries its own linked `imagegen/` root; the app-wide `blastimage:imagegen-root` key stops being the binding of record — *refined during execution*: it survives read-only as the one-time adoption path rather than as a live-root cache, because with the session as the root of record that cache would be a second, competing source of truth (see Implementation Notes)
- [x] Switching project re-points the imagegen link at that project's bound root (or unlinks, when it has none) without an operator action
- [x] Linking a folder binds it to the active project; linking one already bound to a *different* project reports the owner inside the picker modal and offers to switch to it, without ingesting anything
- [x] Because the live root always matches the active project, `resolveDisplayUrl`, `writeSelection`, `promoteApproved`, and `unpromoteApproved` can no longer read or write a different repo's folder for the project on screen — covered by a regression test that switches projects and asserts the resolved root follows
- [x] Existing projects keep working: no `SCHEMA_VERSION` bump, an unbound project loads and behaves exactly as today, and a root already linked under the old global key is adopted by the active project on first load
- [x] The sidebar names the bound folder (e.g. `spinalcord/imagegen`) with the absolute path on hover, instead of the state-only `🔗 imagegen linked`
- [x] Linking a folder while on a still-default, task-less project names that project after the folder's repo (`~/Code/spinalcord/imagegen` → `spinalcord`); a project the operator has named or populated is never renamed
- [x] `npx tsc --noEmit`, `npm run lint`, and `npm test` all pass, with new coverage for the binding, the switch-relink, the collision offer, and the auto-name rule
- [x] Docs that describe linking as an app-wide action are corrected — `README.md`, `docs/WORKFLOW.md`, `docs/REVIEW-LOOP.md`, `CLAUDE.md`

**Discovery Notes:**

**The filed symptom is the visible half of a wider one.** The PLAN line names ingest: `loadRound` drops `batch.json` into whatever project is selected. But round images are stored in session state as *root-relative* `imagegen:rounds/rN/<file>` strings (`lib/imagegenUrl.ts`), and every read and write resolves them against `rootRef.current` — the folder linked *right now*. So re-linking to a second repo does not merely misdirect the next ingest: it silently re-points an *already stored* project's images at the new folder (`resolveDisplayUrl`), and sends that project's `selection.json` merges and `approved/` copies into it (`writeSelection`, `promoteApproved`, `unpromoteApproved`). Same-named files render the wrong image; the rest 404. This is the case for binding rather than merely guarding ingest — and the chosen design closes it *for free*, because if switching project re-links the folder, the live root always matches the project on screen and no call site needs a root argument added.

**One collision point, not two.** With the binding driving the link, a project can never be looking at a foreign root through a switch — the switch re-links. The only way the two can disagree is the operator naming a folder in the picker that another project already owns, which is exactly the one place the operator is present to answer. That is why the collision is reported *inside* the modal (BI-046's rule: an unusable path reports in place without closing) rather than as a global banner or a `window.confirm`.

**The schema does not need to move.** `isSession` (`lib/storage.ts:110`) checks only for `id`/`name`/`schemaVersion`/`tasks`/`refLibrary`/`createdAt`/`updatedAt`; `isSessionMeta` likewise. An added optional field passes both, so `SCHEMA_VERSION` stays at 1 and no migration is written. That matters more than usual here: `loadSession` hard-rejects a version mismatch as `unsupported-version` (BI-030.4), so a bump would have stranded every existing project behind an error until a migration shipped.

**Finding the owner of a root should not deserialize every project.** `listSessions()` reads a lightweight index (`blastimage:index`) precisely so listing never parses full workspaces. Carrying `imagegenRoot` on `SessionMeta` keeps the collision lookup a scan of that index. Old index entries simply lack the field and are refreshed on the owning project's next save.

**Prior art the design follows.** BI-030.3 established that a *structural* break between session state and on-disk files is worth a blocking prompt (renaming a task whose slug already has round images on disk). This is the same class of break at project granularity, which is why it warrants an interruption rather than a banner. BI-043 made round re-ingest idempotent, so re-loading a round into its *own* project stays safe — the guarantee this task keeps intact by ensuring "its own" is now a thing the app can tell.

**Implementation Notes:**

**The link follows the project, so nothing else had to change.** The design's whole leverage is that `resolveDisplayUrl`, `writeSelection`, `promoteApproved`, and `unpromoteApproved` all read one `rootRef`. Making *that* always equal the open project's bound root fixes every one of them without touching a single call site or threading a root argument through the API. `syncImagegenLink` is the one function that maintains the invariant, and every path that changes the open project — mount, switch, create, import — calls it.

**Ownership of the live root moved, and had to move completely.** The provider used to restore a root on mount from its own key. Left in place, that would race the session load and reintroduce the bug: whichever settled last would win. So the restore is gone and the provider now only *serves* whatever it is pointed at. The one deliberate behaviour inside it is that a rejected path **clears** the link instead of leaving the previous one live — switching to a project whose folder has moved must not silently inherit the last project's folder, which is the exact failure the task exists to close.

**Adoption is one-shot, by construction.** `loadStoredRoot()` is read once at mount and `clearStoredRoot()` fires immediately after, success or not. Adopting twice would hand one folder to two projects — the collision this task refuses when the operator does it by hand, so it must not happen behind their back either. A path that no longer resolves is dropped rather than retried forever.

**The collision compares canonical paths, and that is load-bearing.** Both sides come back from `resolveRoot`, which is `realpath` (`lib/imagegenServerFs.ts:60`), so a folder reached by a symlink, a `..` segment, or a trailing slash compares equal to the same folder named directly. Verified live (see Testing Notes) — a raw string compare would have missed exactly the case where the operator does not realise it is the same folder.

**Deviation from Acceptance criterion 1, recorded rather than absorbed.** The criterion assumed the old app-wide key would survive as a live-root cache the provider restores on refresh. With the session as the binding of record that cache is redundant — the active project is loaded on mount and its root re-linked from there — so the key is instead read once for adoption and cleared. Strictly less state, and it removes the second source of truth the criterion would have kept.

**Auto-naming is deliberately narrow.** Only a project still named `My Website` with no tasks is renamed, and it is named after the repo folder *containing* `imagegen/` — every repo's folder is called `imagegen`, so the folder's own name would give every auto-named project the same one.

**Final Summary:**

The `imagegen/` folder is now a property of the project rather than the app. Linking one was app-wide state in a single localStorage key, unrelated to which project was selected — so `loadRound` ingested a batch into whatever happened to be open, and the sidebar never said which repo you were looking at. Binding the root to the `Session` and making every project change re-point the link fixes all of it at one place, because the live root now always matches the project on screen.
