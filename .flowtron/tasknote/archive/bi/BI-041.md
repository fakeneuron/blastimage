## 🎯 Goal

Extract the shared path-resolve loop duplicated by `readImagegenFile` and `writeImagegenTextFile` in `lib/imagegenFs.ts`.

## ⚡ Notes

**Relevance:** Proceed — the duplication and both call sites still exist unchanged since BI-036 deferred it; no new information changes the scope.
**Best Practices Review:** Single-responsibility extraction — the new `resolveImagegenParent` helper owns path-splitting + parent-dir walking only; callers keep their own leaf-handle acquisition (differing options: `getFileHandle` plain vs. `{ create: true }`) and their own empty-path failure mode (throw vs. `Result` error), so no behavior was folded into the helper that the two callers don't already agree on. Dependency direction unchanged — helper is a private (non-exported) function beneath both public exports.
**Drift check:** PLAN.md cited `readImagegenFile` and `writeImagegenTextFile` in `lib/imagegenFs.ts` (lines 210-218 / 257-274 per the sidequest stub, drifted slightly to 206-218 / 249-274 after BI-036's `!` insertions) — read the current file and confirmed both loops still present, near-identical, unchanged since BI-036.
**Archive skim:** `BI-036.md` — this exact deferral, with full rationale ("consolidating them is a behavioral refactor of the FSA seam and outside a config task's remit"). `BI-024.1`/`BI-024.2` — introduced `readImagegenFile`/`writeImagegenTextFile` originally; no further relevant notes on the path-walk shape.
**Pattern survey:** No third path-walk call site exists, so this introduces one new shape (`resolveImagegenParent`) rather than extending an existing one — justified because it's the direct target of BI-036's deferred-cleanup note, and both callers now delegate to it instead of duplicating the loop.
**Implementation:** Added private `resolveImagegenParent(root, relativePath, create)` returning `{ dir, leaf } | null` (null = empty path). `readImagegenFile` calls it with `create=false` and throws on `null`; `writeImagegenTextFile` calls it with `create=true` and returns a `Result` error on `null`. Each caller still does its own leaf `getFileHandle` call with its own options, preserving exact prior behavior.
