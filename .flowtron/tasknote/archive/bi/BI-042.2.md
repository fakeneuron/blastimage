# BI-042.2 | revocation-epoch

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-042]]

## 🎯 Goal

Give blob-URL revocation an observable signal so a mounted `ResolvedImage` re-resolves instead of stranding on a revoked object URL.

## ✅ Acceptance

- [ ] A mounted `ResolvedImage` whose cached blob URL is revoked by `invalidateRoundBlobs` (round reload) re-resolves and ends up on a live blob URL.
- [ ] LRU eviction never revokes a blob URL that a mounted `ResolvedImage` is currently displaying.
- [ ] No re-resolve cascade: resolving more distinct `imagegen:` URLs than `BLOB_CACHE_MAX_ENTRIES` while all are mounted terminates, with no unbounded read/evict loop.
- [ ] Existing `ImagegenContext` contracts hold: recency bump on hit, round-scoped invalidation, unmount revokes everything.
- [ ] Existing `ResolvedImage` contracts hold: passthrough for `data:`/`https:`, re-resolve on `src` change and on `linked` (BI-038), stale-in-flight loses to newer `src`, read failure falls back to the raw URL.
- [ ] `npx vitest run lib/ImagegenContext.test.tsx components/ResolvedImage.test.tsx` passes; `npm run lint` + `npx tsc --noEmit` clean.

## 🧩 Subtasks

- [ ] Add `blobEpoch` state to `ImagegenProvider`, bumped only where a revoke can strand a mounted consumer (`invalidateRoundBlobs` via `readRound`) — never from the eviction path.
- [ ] Add a `displayedRef` set of currently-rendered blob URLs; `evictOldestBlob` walks past held entries to the oldest evictable one, and no-ops when every entry is held (soft bound).
- [ ] Expose `blobEpoch` plus `retainDisplayUrl`/`releaseDisplayUrl` on `ImagegenApi`; mirror them in `NOOP_IMAGEGEN` (`lib/useWorkspace.ts`).
- [ ] `ResolvedImage`: add `blobEpoch` to the effect deps; retain the resolved URL on success and release it on cleanup.
- [ ] Add a provider-level test that a round reload bumps `blobEpoch` and that eviction skips held URLs (full component-level consumer-recovery contract stays in BI-042.3).
- [ ] Run targeted tests + lint + typecheck.

**Discovery Notes:**

**Root cause.** `resolveDisplayUrl` hands a consumer an object URL and the provider later revokes it on two paths, neither of which the consumer can observe:

| Path | Trigger | Intent | Re-resolving is… |
|---|---|---|---|
| `invalidateRoundBlobs` | `readRound(N)` — a round reloaded, possibly rewritten on disk | **staleness** | …exactly right |
| `evictOldestBlob` | cache reached `BLOB_CACHE_MAX_ENTRIES` | **memory bound** | …self-defeating |

`ResolvedImage`'s effect deps are `[src, resolveDisplayUrl, linked]`; `resolveDisplayUrl` is a stable `useCallback([])` and neither `src` nor `linked` moves on a revoke, so the component keeps rendering a dead `blob:` URL for the life of the mount.

Reachable today: approve an r1 image (its gallery thumbnail now holds a cached blob URL), rerun `/blast-generate` against r1, then **↻ Load round** r1. `readRound` revokes the thumbnail's URL; the review grid recovers only incidentally, because `ingestRoundBatch` mints fresh image ids and remounts those cards. The gallery thumbnail — keyed by the *old* `imageId` — does not remount, and stays blank.

**Why the filed mechanism fails.** One global epoch bumped on *every* revoke turns the eviction path into a non-terminating loop whenever mounted images outnumber the cache bound. With 201 mounted and a bound of 200: resolving #201 evicts #1 → bump → all effects re-run → #1 misses → reads → inserts → evicts #2 → bump → … Each cycle also issues a real FSA read. The bug being fixed is a blank image; the fix as filed would be a hung page. Not typical (it needs 200+ concurrent `imagegen:` images — a very large bulk review or approved gallery), but it is a strictly worse failure mode and it is knowable now.

The asymmetry in the table is the whole design constraint: **invalidation wants consumers to react; eviction wants them not to exist.** One signal cannot serve both.

**Recommended shape (option B below).** Split the two paths:
- `blobEpoch` state, bumped **only** by `invalidateRoundBlobs`. Staleness re-resolves; no cascade, because invalidation re-reads the same URLs it dropped and causes no net growth.
- A `displayedRef: Set<string>` of blob URLs a mounted `ResolvedImage` currently shows. `evictOldestBlob` walks past held entries to the oldest evictable one and no-ops when all are held — the bound goes soft rather than stranding a live image. Entries become evictable the moment they unmount, which is precisely the "previous rounds age out" behaviour BI-029.4 sized the cache for.

Cost: ~20 lines and two new `ImagegenApi` members (`retainDisplayUrl` / `releaseDisplayUrl`) beyond the filed one.

**Final Summary:**

A `ResolvedImage` no longer strands on a dead `blob:` URL when the provider revokes the one it is displaying. The two revocation paths are now treated as the opposites they are: a **round reload** (staleness) bumps a `blobEpoch` that consumers list in their resolve-effect deps, so they re-resolve onto the new bytes; **LRU eviction** (memory bound) instead skips any blob URL a mounted consumer is holding, so it never breaks what is on screen.

**Verification:** `npm test` 25 files / 417 passed (was 411) · `npx tsc --noEmit` clean · `npm run lint` clean. Both behaviours mutation-checked — disabling the held-set skip fails 3 eviction tests; removing the epoch bump fails the bump test.

**Refactors:** two, both required by Acceptance — `evictOldestBlob` now finds the oldest *evictable* entry rather than the oldest entry, and `invalidateRoundBlobs` returns a revoked count so the epoch only bumps on a real revocation. Deferred as filed: `useMemo` on the context value ([[BI-042.4]]), component-level consumer-recovery contract ([[BI-042.3]]).
