# BI-029.4 | blob-cache-bounds

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-029]]

## 🎯 Goal

Bound the `ImagegenContext` blob-URL cache and invalidate a round's entries on `loadRound`, so it no longer grows unboundedly or serves stale blobs after a terminal rewrite of a round's files.

## ✅ Acceptance

- [ ] `ImagegenContext`'s blob-URL cache (`blobCacheRef`, in `resolveDisplayUrl`) is capped at a fixed maximum entry count; inserting past the cap evicts the least-recently-used entry and revokes its object URL (no unbounded growth for the life of the session).
- [ ] `ImagegenApi.readRound` (called by `useWorkspace.loadRound`) revokes and removes any cached blob-URL entries belonging to the round being (re)loaded before reading — a subsequent `resolveDisplayUrl` call for that round's images always re-reads bytes from disk instead of returning a stale cached blob.
- [ ] Cache entries for other rounds are left untouched by a `readRound` invalidation.
- [ ] `npx tsc --noEmit`, `npm run lint`, and `npm test` all pass.

## 🧩 Subtasks

- [ ] `lib/ImagegenContext.tsx`: add a `BLOB_CACHE_MAX_ENTRIES` bound + LRU-ish eviction (move-to-end on hit, evict-oldest-on-overflow) in `resolveDisplayUrl`.
- [ ] `lib/ImagegenContext.tsx`: add a module-level `invalidateRound(cache, round)` helper (using `roundNumberFromImageUrl` from `./imagegenUrl`) and call it from `readRound` before `readRoundBatch`.
- [ ] New `lib/ImagegenContext.test.tsx`: cover cache-bound eviction (oldest entry revoked once the cap is exceeded) and round invalidation on `readRound` (revokes + drops only the matching round's entries; other rounds stay cached).
- [ ] Verify: `npx tsc --noEmit`, `npm run lint`, `npm test`.

- [x] Asked clarifying questions OR logged "No clarifications needed" with explicit assumptions

  **No clarifications needed.** Explicit assumptions:
  1. **Bound value is an implementation judgment call**, not specified by the PLAN line. Chosen: 200 entries — generous enough to hold several fully-loaded rounds of review images at once (avoids visible re-fetch churn while browsing back and forth within a session) while still capping worst-case memory/handle growth for a long-running session. No acceptance criterion depends on the exact number, only that a bound exists and is enforced.
  2. **Eviction policy is LRU** (recency-bumped on cache hit, oldest evicted on overflow) rather than plain FIFO — cheap with a `Map` (delete+re-set on hit) and keeps recently-viewed images resident even if they were cached early, which is the behaviour a reviewer flipping between images would expect.
  3. **Invalidation scope is exactly the round passed to `readRound`.** `loadRound` is `readRound`'s only caller, and it always passes the round about to be (re)displayed — invalidating that round's entries there covers "on `loadRound`" from the PLAN line without adding a new `ImagegenApi` member or threading state through `useWorkspace`.
  4. **`resolveBlob`/`resolveImageBlob` (BI-029.2) is out of scope** — it is deliberately uncached (reads fresh bytes every call per its own docstring), so it has neither a growth nor a staleness problem to fix.

**Discovery Notes:**

The two symptoms in the PLAN line share one root cause: `blobCacheRef` treats every `imagegen:` URL as immutable once resolved, which was true for the epic's original scope (render-time resolution of round images that don't change) but stops being true the moment a round can be *rewritten* in place (rerunning `/blast-generate` against an existing `rounds/r<N>/` — same filenames, new bytes) — and separately, nothing ever shrinks the cache for the lifetime of the single `ImagegenProvider` mount. Both fixes are additive to `resolveDisplayUrl` / `readRound` and require no change to `ImagegenApi`'s public shape, `useWorkspace.ts`, or any render consumer.

**Implementation Notes:**

- **`lib/ImagegenContext.tsx`** (+34/−4) — `BLOB_CACHE_MAX_ENTRIES = 200` (module constant, documented rationale) plus two private helpers: `evictOldestBlob(cache)` (revokes + drops the `Map`'s oldest key) and `invalidateRoundBlobs(cache, round)` (revokes + drops every entry whose `roundNumberFromImageUrl` matches, imported from `./imagegenUrl`). `resolveDisplayUrl`'s cache-hit branch now does `delete`+`set` to bump recency before returning; its cache-write branch calls `evictOldestBlob` once `cache.size >= BLOB_CACHE_MAX_ENTRIES` before inserting. `readRound` calls `invalidateRoundBlobs(blobCacheRef.current, round)` before `readRoundBatch`, so any stale entries for that round are gone before the round's images can be re-displayed.
- No other file changed — `ImagegenApi`'s public shape, `useWorkspace.ts`, `NOOP_IMAGEGEN`, and every render/byte consumer (`ResolvedImage`, `GalleryPanel`, `lib/storage.ts`) are unaffected; the fix is entirely internal to the context's own cache lifecycle.
- **`lib/ImagegenContext.test.tsx`** (new, 100 lines) — the repo's first `lib/*.test.tsx`; mocks `./imagegenFs` (`restoreLinkedImagegenFolder`, `readImagegenFile`, `readRoundBatch`) since `ImagegenContext` has no injection point into that module (same rationale `components/Workspace.test.tsx` records for mocking `useWorkspace`), and stubs `URL.createObjectURL`/`revokeObjectURL` per the `lib/storage.test.ts` convention. Drives the real provider/hook via `renderHook` + `ImagegenProvider` wrapper. Three tests: (1) inserting `BLOB_CACHE_MAX_ENTRIES + 1` entries evicts exactly the first-inserted one; (2) a cache hit does not evict (recency bump proven by returning the same blob URL, zero revokes); (3) `readRound(1)` revokes + drops round 1's cached entry only — a subsequent `resolveDisplayUrl` for that URL returns a *new* blob URL (cache miss), while round 2's entry is untouched (same cached URL returned, no re-read).

**Final Summary:**

`ImagegenContext`'s display-blob cache (`resolveDisplayUrl`) grew unbounded for the life of the single `ImagegenProvider` mount — object URLs were only revoked on unmount, which never happens in practice — and never invalidated a round's entries on reload, so a round rewritten on disk (e.g. a rerun of `/blast-generate` against an existing `rounds/r<N>/`) could serve a stale cached blob. The cache is now capped at 200 entries with LRU eviction (recency-bumped on hit, oldest revoked on overflow), and `readRound` revokes + drops a round's cached entries before it is (re)read, so a reload always shows current bytes.
