# BI-067.3 | Extract Sidebar inline draft input into SidebarDraftInput

[← PLAN.md](../PLAN.md) · 🌱 Starter (filed 2026-10-15)

## 🌱 Starter context

_Captured 2026-10-15 during /ft-refactor survey of components/. Promote at `/ft-task BI-067.3`._

### Why this exists

The new/rename draft input is self-contained state inside Sidebar.tsx: `draftKind`, `draftKindRef` (guards double submit when Enter unmounts the input and blur fires), `draftInputRef`, and four handlers. Pulling it into its own component shrinks Sidebar.tsx. It comes second because BI-067.2 must pin its behavior first.

### Solution shape

- New `components/SidebarDraftInput.tsx` owning the input element, its ref, the Enter/Escape key handling, and the submit-once guard.
- Sidebar.tsx keeps the draft-open state it needs to decide where the input renders, and passes callbacks in.
- Behavior-preserving. Sidebar's public props are unchanged. Existing and BI-067.2 tests stay green with no assertion changes.
- The `draftKindRef` double-submit guard moves with the input; keep the comment explaining why it is a ref, not state.

### Files to touch (preliminary survey — drift-check at promotion)

- `components/Sidebar.tsx` — remove draft handlers and input JSX (~lines 133–200, plus the draft JSX)
- `components/SidebarDraftInput.tsx` — new file

### Explicitly out of scope

- Project ⋯ menu — BI-067.4
- Any change to what Sidebar's props mean or how the parent Workspace calls it

### Decisions locked in this conversation

| Decision | Choice | Rationale |
|---|---|---|
| Component boundary | Input element plus its key/submit handling, not the task list | Keeps the seam narrow; the list stays in Sidebar |
| Props | Sidebar public props unchanged | Keeps Workspace.tsx and app/page.tsx untouched |

### Open at promotion (Phase 1 should resolve)

- Whether the draft state stays in Sidebar or moves into the new component. Lean: Sidebar keeps the state, the component keeps the input and key handling.
