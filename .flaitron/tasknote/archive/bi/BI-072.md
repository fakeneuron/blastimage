# BI-072 | imagegen-symlink-confinement

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-045]] · [[CORE-013]]

## 🎯 Goal

Close the two symlink confinement gaps in `lib/imagegenServerFs.ts`, failing closed: a dangling symlink can no longer steer a write outside the linked root, and `listRounds` can no longer read a `batch.json` symlinked from outside it.

- [x] `listRounds` skips a round whose `batch.json` is a symlink to a file outside the root; in-root rounds still list — `npx vitest run lib/imagegenServerFs.test.ts`

## 📝 Phase 1: Discovery

- [x] Reviewed the task entry in PLAN.md

- [x] **Relevance Assessment**

  **Verdict:** Proceed
  **Rationale:** Both gaps are in current code exactly as filed. (1) `canonicalOrParent` treats any `realpath` failure as "absent" and walks to the parent, so a dangling symlink at `approved/<name>` passes on the root's canonical path; `copyFile` then follows the link and creates its target outside the root. (2) `listRounds` reads `join(roundsDir, entry.name, 'batch.json')` without `resolveUnderRoot`. Neither has been fixed since filing earlier today.

- [x] Read relevant source files — `lib/imagegenServerFs.ts` (whole), `lib/imagegenServerFs.test.ts` (confinement, listRounds, approved suites), and the exact-message assertions in `lib/imagegenApprovedRoute.test.ts`

- [x] **Best Practices Review** — The fix stays inside the single confinement chokepoint (`resolveUnderRoot` → `canonicalOrParent`), so every caller inherits it at once and no route changes. `listRounds` is the one reader that skipped the chokepoint; routing it through closes the bypass without a new abstraction. It cannot reuse `readBatchText(root, round)`, because `ROUND_DIR_RE` accepts `r01`, and `readBatchText` would rebuild that path as `r1`. The helper resolves `rounds/${entry.name}/batch.json` instead, which keeps the listing reading the folder it found.

- [x] **Archive skim** — 22 hits across bi/core/deployment/test; I grepped the load-bearing ones for confinement history. BI-045 designed the realpath confinement and the canonical-root precondition (prefix compare, so roots must be `realpath`'d). It tested a symlink escape on an *existing* target only, so the dangling case was never covered. BI-062 noted that `approved/..` resolves to the root (refused downstream by EISDIR) and touched nothing related. TEST-012.3 added route-level symlink escape tests for `approved` (GET/POST/DELETE) that assert the exact string `Path escapes the linked imagegen folder: <path>`, so the new refusal must use that same message. `approvedConflict` also tells a refusal apart from "nothing there" by that prefix. No archive note mentions dangling links or `lstat`.

- [x] **Drift check** — Cited functions (`resolveUnderRoot`, `canonicalOrParent`, `listRounds`, `promoteApproved`, `approvedConflict`) and the test file all match current code. `lib/imagegenServerFs.ts` is the only `node:fs` importer under `app/` and `lib/` (non-test), so no other reader bypasses the chokepoint. The plan matches the PLAN.md line, with one widening logged below.

- [x] No clarifications needed. Explicit assumptions:
  1. **Walk-wide, not leaf-only.** The PLAN line says to `lstat` the leaf. The walk in `canonicalOrParent` visits the leaf first and then each missing ancestor, so applying the same check at every failed probe also covers a dangling *intermediate* (e.g. `approved` → a nonexistent dir outside). It costs no extra code. It is strictly more fail-closed and within the line's stated rule ("drop anything not provably inside the root").
  2. **Refuse, don't follow.** A dangling link is refused even when it points inside the root; resolving its target via `readlink` would need loop handling and is not what the line asks for. Normal imagegen folders hold no dangling links.
  3. **Same error string.** The refusal reuses `Path escapes the linked imagegen folder: <relativePath>`, so `approvedConflict`'s prefix check and the route suites' exact-message assertions keep working unchanged.
  4. `removeApproved` on a dangling `approved/<name>` link is now refused rather than unlinking it. That is consistent with how an existing out-of-root link is already treated, and acceptable.
  5. TOCTOU (a link swapped between check and use) stays out of scope, as it was in BI-045.

- [x] Subtasks above populated with ordered steps; YAML `touches:` declared (omit only with no file deliverable)

**Discovery Notes:**

The leak path for gap (1), traced: `promoteApproved` → `resolveUnderRoot(root, 'approved/x.png')` → lexical check passes → `canonicalOrParent`: `realpath(approved/x.png)` throws ENOENT (dangling) → probe `approved` → resolves to `<root>/approved` → inside → `{ ok: true }`. Then `copyFile(src, <root>/approved/x.png)` opens the destination with O_CREAT, which follows the link and creates the outside target. `approvedConflict` reads via `readImagegenBytes`, whose `readFile` also follows the link and fails ENOENT. That failure is a non-`Path escapes` error, so it reports "no conflict".

**Implementation Notes:**

- Pattern: extended the existing chokepoint. `canonicalOrParent` now returns the module's own `Result` type (`Result<string | null>`) rather than a bare `string | null`. When `realpath` fails, it runs `lstat` on the probe; an entry that exists but won't resolve fails the walk. `resolveUnderRoot` folds that failure into its existing escape condition and returns the unchanged `Path escapes the linked imagegen folder: <path>` string. That keeps `approvedConflict`'s prefix check and TEST-012.3's exact-message route assertions working without edits.
- `listRounds` resolves `rounds/${entry.name}/batch.json` through `resolveUnderRoot` and skips on refusal. A one-line comment records why it uses `entry.name` rather than `readBatchText(round)`: `r01` is its own folder.
- Doc comments: `resolveUnderRoot` and `canonicalOrParent` now state the dangling-link rule.
- Tests first: four new cases (dangling leaf, dangling dir, approve/conflict through a dangling leaf asserting nothing is created outside, symlinked `batch.json`) all failed against the unfixed code (`4 failed | 36 passed`), then passed after the fix.
- No refactor beyond the helper's return type, which the fix required.
