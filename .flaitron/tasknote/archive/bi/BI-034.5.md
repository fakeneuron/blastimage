# BI-034.5 | secret-scan-decision

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-034]]

## 🎯 Goal

Decide whether blastimage adopts natabula's `.gitleaks.toml` + `.pre-commit-config.yaml` secret-scan deposits, and either land them or record the opt-out.

## ⚡ Notes

**Relevance:** Proceed — the PLAN line's premise holds exactly. Neither `.gitleaks.toml` nor `.pre-commit-config.yaml` existed at repo root, and both deposits are Tier-1 base-stable in natabula (`docs/MIGRATION.md` §2.1 core table). The line delegates a genuine either/or, so the decision was put to the operator with measured evidence rather than taken unilaterally; the operator chose **adopt both + arm the hook**.

**Best Practices Review:** No abstraction or dependency-direction concern — two declarative configs, byte-copied, plus a five-line README block. Duplication: none; the two files are deliberately *not* forked, so `/natabula-layer-refresh` can keep refreshing them byte-for-byte. Resisted two tempting additions: a `just secrets` verb (the fleet's own `justfile` deposit carries no secret-scan recipe, so inventing one here would create per-repo divergence in a base-stable file) and a repo-local allowlist (nothing to suppress — see verification). Deferred: nothing unrelated touched.

**Drift check:** No drift. The natabula sources exist at `configs/.gitleaks.toml` and `configs/.pre-commit-config.yaml` as the PLAN line implies, and both are clean at natabula HEAD `6af815d` — the copies here are byte-identical to that SHA. `/natabula-layer-refresh` was **not** invoked as the mechanism: it is a cross-repo interactive refresher for files that already exist and have diverged, and blastimage had neither file, so a direct copy from the same source is the same result with less ceremony. The `.gitleaks.toml` allowlist paths (`.flowtron/tasknote/archive/`, `.env.example`) match real paths in this repo.

**Archive skim:** `grep -rl -iE "gitleaks|pre-commit|secret scan"` over `archive/{bi,core,test}/` returns three files — all **false positives**: `BI-032`, `BI-030.2`, and `BI-033` use "pre-commit" in the unrelated *session-state* sense (reading the pre-commit `session` object before a state commit). No prior tasknote has ever touched secret scanning. `BI-001.md` is the only natabula-layer hit; it read `STACK-TENDENCIES.md` for stack conventions (Tailwind, flat layout) and never reached the deposit tiers. So there is no precedent constraining this adoption in either direction.

**Pattern survey:** The deposits are byte-copies of the fleet baseline — the established shape for Tier-1 base-stable files, and the reason `/natabula-layer-drift` can classify them as `=`. Fleet adoption is thin (marscharts, neromercato carry both; finanal carries `.gitleaks.toml` alone; 18 other roots carry neither), but that is the documented *lazy backfill* posture, not a signal against adoption. The README addition extends the existing "Install & Run" fenced-block idiom rather than opening a new Contributing section.

**Implementation:** Three files, no source touched.

`.gitleaks.toml` + `.pre-commit-config.yaml` — byte-identical copies of natabula HEAD `6af815d`, verified with `diff -q` after the copy. Left unmodified on purpose: no repo-local allowlist was added because none is needed (see verification), and adding a speculative one would be the exact "project-specific noise in the shared baseline" the deposit's own header warns against.

`README.md` — five lines under "Install & Run" documenting the arming step. This is the one addition beyond a pure byte-copy and it is load-bearing rather than decorative: the deposit's failure mode is **silent**. `.pre-commit-config.yaml` scans nothing until `pre-commit install` writes `.git/hooks/pre-commit`, that file is untracked, and so arming is **per clone, not per repo** — a fresh checkout on another machine inherits a config that looks armed and isn't. natabula's own doctrine calls this state "worse than no deposit at all," so the prerequisite belongs in the README rather than only in a closed tasknote.

**Verification:** Both prerequisites were already present on this machine (gitleaks 8.30.1 via brew, pre-commit 4.6.1 via uv), so adoption needed no new install. `pre-commit install` ✅ · `pre-commit validate-config` ✅.

*Negative control (does it stay quiet?)* — the full HEAD tree, extracted via `git archive` and scanned standalone, reports **0 leaks with the allowlists and 0 with the bare default ruleset**. The allowlists are therefore doing no work here yet; the repo is genuinely clean, so the hook lands silent and needs no tuning.

*Positive control (does it actually fire?)* — this is the check that matters, given the silent failure mode. A first attempt with hand-written AWS-shaped strings **passed**, which looked like a broken hook but was bad test data: the bare default ruleset didn't flag those strings either, so gitleaks' AWS rules never matched. Re-run with a `ghp_`-prefixed PAT and a well-formed HS256 JWT, both confirmed detectable by the bare ruleset first, the hook **Failed with `leaks found: 2`** and `git commit` was genuinely blocked — HEAD verified still at `889d44b` afterwards. Control file unstaged and deleted; `git status` clean apart from this task's deliverables.

*Gates* — typecheck ✅ · lint ✅ · 213 tests / 15 files ✅. Not expected to move (no source changed), run to confirm the two new root dotfiles aren't picked up by an eslint or vitest glob.

**Docs touched:** `README.md` — **updated** (arming block under "Install & Run", per the per-clone rationale above). `AGENTS.md` — no change (flowtron workflow prose and the paste-block; documents no local tooling setup). `CLAUDE.md` — no change (Stack section covers framework/state/testing; a commit hook is neither a stack choice nor a test convention, and the README now carries it). `.flowtron/PLAN.md` — flipped this task's line at closure.

## ✅ Recap

Adopted both secret-scan deposits. `.gitleaks.toml` + `.pre-commit-config.yaml` are byte-identical copies of natabula HEAD `6af815d`, the hook is armed, and `README.md` gained a five-line arming block. Three files, no source touched.

The PLAN line delegated adopt-or-opt-out, and the evidence made adoption cheap rather than merely defensible: both prerequisites were already installed, and the HEAD tree scans clean *even under the bare default ruleset*, so the gate lands silent with no allowlist tuning and no day-one failure. The opt-out case was real but time-limited — blastimage is localStorage-only with zero environment variables today, yet it carried Supabase credential config through BI-022.x until BI-028 removed hosted mode, and `.env.example` explicitly anticipates future server-side Neon/R2 credentials. Adopting now means the gate is already in place when that surface returns, instead of being remembered at the moment it starts to matter.

Three things a later `/ft-audit` pass should know.

First, **the positive control is the verification that counts, and it initially misfired.** A config with no working runner passes every commit silently, which is indistinguishable from a clean repo — so "no findings" is not evidence the hook works. My first control used hand-written AWS-shaped keys and passed; that was bad test data, not a broken hook (the bare ruleset missed them too). A `ghp_` PAT and a well-formed JWT both fire, and a real `git commit` was blocked with HEAD confirmed unchanged. Anyone re-verifying this should use shapes confirmed detectable by the bare ruleset first.

Second, **arming is per clone, not per repo.** `pre-commit install` writes an untracked `.git/hooks/pre-commit`, so a fresh checkout has the config and no hook. That is why the README block exists and why it should not be trimmed as redundant.

Third, **CI still has no secret-scan step** — the NAT-117 spine gate. This was offered and deliberately declined as beyond the PLAN line's scope (`/natabula-layer-refresh` excludes `ci.yml` by design, NAT-093). Recording the trap for whoever adds it later: `gitleaks dir .` does **not** respect `.gitignore`, and blastimage's build output yields 6 `generic-api-key` hits on Next's own `previewModeSigningKey` / `previewModeEncryptionKey` / `encryptionKey` in `.next/`. The step must therefore run **before** `Build` in `ci.yml`, or exclude `.next/` explicitly — otherwise it fails on day one against framework-generated keys that are not secrets. Not filed as a task; the commit-time hook is the instrument that actually prevents history contamination, and CI is a backstop.

Maintainability effect: net positive, at near-zero ongoing cost. The repo gains the one instrument that can stop a credential *before* it enters history, the two files stay refreshable by `/natabula-layer-refresh` because nothing was forked, and per-commit overhead measured ~20–50 ms.
