**Discovery Notes:**

- Phase 1→2: Discovery surfaced no significant deviation → skip 🛠️.
- Cause, per element: the **Found-nearby** section sits *above* Link path, so it pushes the button down by its own height *and* (centered) the dialog grows both ways. The **error** / **owned** banners sit *below* the form, so they move Link path only through re-centering. Top-anchoring therefore fixes the banners entirely but not the suggestions; the suggestions need reserved space. The PLAN row's "top-anchor or reserve space for both" resolves to: top-anchor (banners) + reserved slot (suggestions).
- Reserved slot: `h-[5.5rem]` = heading (16px) + gap (8px) + two rows (30px each) + row gap (4px) = 88px; scrolls past two suggestions. Cost: a blank band when nothing is found nearby, the common case. Accepted: the alternative (moving the section below the form) demotes the primary one-click path.
- Best practices: presentational modal only, no new abstraction; two class changes.
- Archive skim (area `bi`, README table checked): BI-069 (predecessor; noted this exact follow-up), BI-046, BI-050, BI-068, BI-047, BI-049, BI-051, BI-053.2, BI-061, BI-065 mention the modal; none records a layout contract beyond BI-069's list height.
- Drift check: PLAN row matches source; `e2e/imagegen-link-layout.spec.ts` exists as described; suggestions come from `GET /api/imagegen/link`, errors from `POST /api/imagegen/link` with a bad path.
- No clarifications needed (--unattended): assume a reserved blank band for suggestions is acceptable UX.
