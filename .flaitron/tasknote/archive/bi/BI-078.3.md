**Implementation Notes:**

- `app/api/imagegen/file/route.ts`: `mp4: 'video/mp4'`; `parseByteRange(header, size)` → span / `'unsatisfiable'` / `null` (ignore). The handler sends `Accept-Ranges: bytes` on every served file, a 206 with `Content-Range` + `Content-Length` for a span, a 416 with `Content-Range: bytes */size` and no `Content-Type` for an unsatisfiable range, and the full 200 otherwise. A request carrying `If-Range` gets the full 200: the route sends no validator, so none can match (RFC 9110).
- `lib/imagegenFileRoute.test.ts`: parser cases (three forms, clamping, unsatisfiable, ignored) plus handler cases (206 slice + headers, Safari's `bytes=0-1` probe, 416, multi-range fallback, If-Range fallback, Accept-Ranges on 200).
- `e2e/clip-playback.spec.ts`: builds a bare `<video>` on the app origin pointed at `test-fixtures/imagegen-clip/rounds/r1/hero-banner-001.mp4` through the route; asserts no media error, `readyState >= 1`, duration > 0; on webkit also awaits a 206 response.
- **Negative control (BI-078.1's open risk, now settled).** With range handling stubbed out, chromium still passed but webkit failed with `media.error.code` 4 (MEDIA_ERR_SRC_NOT_SUPPORTED). Safari does need 206; the MIME type alone was not enough. Playwright's Chromium does load this H.264 fixture's metadata.
