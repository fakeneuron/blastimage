# BI-029.2 | resolve-image-blob-seam

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-029]]

## 🎯 Goal

Introduce a single `resolveImageBlob(url)` helper as the sole URL→bytes path in the app, and route the three byte-consuming call sites — `gatherExportFiles`, `gatherReviewImages` (lib/storage.ts) and `GalleryPanel.downloadImage` — through it so `imagegen:` URLs resolve through the linked folder instead of a bare `fetch()` that cannot succeed.

## ✅ Acceptance

- [ ] A single helper resolves any stored image URL to bytes: `imagegen:` paths read through the linked `imagegen/` root; `data:` and `https:` URLs keep their existing `fetch` behaviour.
- [ ] `gatherExportFiles`, `gatherReviewImages`, and `GalleryPanel.downloadImage` all obtain bytes through that helper — no bare `fetch(approved.url)` / `fetch(url)` remains on an image URL.
- [ ] The helper is reachable from `lib/storage.ts` without `lib/storage.ts` importing React context (dependency direction preserved: `imagegenFs` → `storage`, never the reverse at runtime).
- [ ] An unlinked folder + an `imagegen:` URL degrades exactly as a failed fetch does today (counted in `failedImages` / `failed`, surfaced via `UseWorkspace.error`) — no throw escapes to the UI.
- [ ] `npx tsc --noEmit`, `npm run lint`, and `npm test` all pass.

## 🧩 Subtasks

- [ ] `lib/imageBlob.ts` (new): `ImageBlobResolver` type + `resolveImageBlob(url, root)` — FSA read for `imagegen:` URLs, `fetch` otherwise, throws with a user-facing message when an `imagegen:` URL is seen with no linked root.
- [ ] `lib/ImagegenContext.tsx`: add `resolveBlob: (url) => Promise<Blob>` to `ImagegenApi`, bound to `handleRef.current`.
- [ ] `lib/storage.ts`: thread an `ImageBlobResolver` param through `gatherExportFiles`, `gatherReviewImages`, and the three public entry points (`exportManifestToFolder`, `downloadManifestBundle`, `downloadReviewSheet`).
- [ ] `lib/useWorkspace.ts`: give `NOOP_IMAGEGEN` a `resolveBlob`, and pass `imagegen.resolveBlob` at the three export call sites.
- [ ] `components/GalleryPanel.tsx`: take `resolveBlob` from `useImagegen()`; skip the `window.open` fallback for `imagegen:` URLs (nothing useful to open).
- [ ] Tests: unit-cover `resolveImageBlob` (both branches + unlinked); update existing `lib/storage.test.ts` export suites to the new signature.
- [ ] Verify: `npx tsc --noEmit`, `npm run lint`, `npm test`.

- [x] **Best Practices Review**

  **Touched responsibilities.** `lib/storage.ts` = pure/DOM persistence + export encoding; `lib/imagegenFs.ts` = FSA seam; `lib/ImagegenContext.tsx` = React binding of that seam. **Dependency direction today is `imagegenFs` → `storage`** (`supportsDirectoryPicker`, `Result`), so `storage.ts` must not import the context or the FSA module at runtime — the resolver has to arrive by injection, not by import.

  **Chosen shape (extends an existing pattern, no new one invented):** callback injection, same as `ingestRoundBatch(session, batch, imageUrlFor)` (`lib/workspace.ts:203`) and `useWorkspace(imagegen)`. `storage.ts` takes an `ImageBlobResolver` parameter; `ImagegenProvider` binds the one implementation to its handle ref. Rejected alternatives: a module-level setter installed by the provider (global mutable state), and moving the gather functions into a context-aware module (they are non-React encoders that belong with the export encoding).

  **Duplication check.** `resolveDisplayUrl` is deliberately *not* routed through the new helper: it must return `url` unchanged for `data:`/`https:` (no fetch) and mints cached blob URLs. Both paths already share the real primitive, `readImagegenFile` — the residual overlap is one line, so an abstraction over the two would cost more than it saves.

  **In-scope refactor:** none beyond the signature threading. **Deferred:** the blob-URL cache bounds/invalidation ([[BI-029.4]]) and the export error copy (`"could not be fetched"` is now imprecise for the unlinked case, but the message surface belongs to [[BI-031.2]]'s error-copy pass).

**Discovery Notes:**

The bug is a **scheme/consumer mismatch**, not a missing feature: `imagegen:` is a private URL scheme with exactly one resolver (`readImagegenFile`), and only the render path was ever wired to it. The fix is to give the byte path the same single resolver, and to make that resolver the *only* way bytes are obtained — so a fourth URL class added later fails loudly in one place instead of silently in three.

Notably, the folder export is partly redundant in adopter mode: approving already copies the keeper into `imagegen/approved/` via `promoteKeeperToApproved` (`lib/imagegenFs.ts:331`). But `manifest.json` and `review.html` are only produced by the export path, and `docs/ADOPT.md` §"`approved/`" documents all three Gallery actions as the way to land them — so the export path stays load-bearing.

- [x] **Pattern survey** — extended an established pattern or justified a new shape; checked DRY and single-responsibility (SRP) boundaries; preferred composition when it reduced coupling

  Extended the codebase's existing **callback-injection** shape rather than inventing one: `ingestRoundBatch(session, batch, imageUrlFor)` (`lib/workspace.ts:203`) already hands a pure module its URL policy as an argument, and `useWorkspace(imagegen)` already receives the FSA surface by parameter. `ImageBlobResolver` follows both. SRP holds: `imageBlob.ts` owns *URL class → bytes*, `imagegenFs.ts` owns *FSA reads*, `storage.ts` owns *export encoding*, `ImagegenContext` owns *binding the root*. Composition over coupling — `storage.ts` gained a parameter, not an import of the FSA/React layers.

- [x] **Minimal refactor gate** — refactored only for Acceptance or to prevent duplication, obscured responsibility, or a dependency-boundary violation in the touched path; recorded the reason and deferred unrelated cleanup

  Only the signature threading required by Acceptance. `resolveDisplayUrl` was deliberately **not** rewritten on top of `resolveImageBlob`: it must return `data:`/`https:` URLs untouched (no fetch) and mint cached blob URLs, so routing it through a bytes resolver would add a network round-trip to the render path. Both already share `readImagegenFile`. Deferred: blob-cache bounds ([[BI-029.4]]), the now-imprecise "could not be fetched" copy ([[BI-031.2]]).

**Implementation Notes:**

- **`lib/imageBlob.ts`** (new, 38 lines) — `ImageBlobResolver` + `resolveImageBlob(url, root)`. `imagegen:` → `readImagegenFile(root, imagegenPathFromUrl(url))`; everything else → `fetch(url).blob()`; throws a user-facing message when an `imagegen:` URL arrives with no linked root. The root is a parameter, not an import, which is what lets `lib/storage.ts` depend on the *type* only and keeps the runtime direction `imagegenFs` → `storage` intact.
- **`lib/ImagegenContext.tsx`** — `ImagegenApi.resolveBlob: ImageBlobResolver`, a `useCallback` binding `handleRef.current` into `resolveImageBlob`. Sits beside `resolveDisplayUrl` as the bytes twin of the display resolver.
- **`lib/storage.ts`** — `gatherExportFiles` / `gatherReviewImages` take the resolver and call it in place of `fetch(approved.url)`; propagated through the three public entry points (`exportManifestToFolder`, `downloadManifestBundle`, `downloadReviewSheet`). Per-image `try`/`catch` is unchanged, so an unresolvable image still degrades into the existing `failed` count rather than throwing. Doc comments updated where they asserted "fetched to a blob" / "whose fetch failed".
- **`lib/useWorkspace.ts`** — passes `imagegen.resolveBlob` at the three call sites; `NOOP_IMAGEGEN.resolveBlob = (url) => resolveImageBlob(url, null)`, so the no-provider path keeps working for `data:`/`https:` and rejects `imagegen:` honestly.
- **`components/GalleryPanel.tsx`** — `const { resolveBlob } = useImagegen()` (already rendered under `ImagegenProvider` via `Workspace.tsx:28`); `downloadImage` takes the resolver, and its `window.open` fallback is now skipped for `imagegen:` URLs, which no browser can open.
- **Verified `resolveImageBlob` is genuinely the sole path**: `grep -rn "fetch(" lib components app` (excluding tests) returns exactly one hit — `lib/imageBlob.ts:37`.

**Final Summary:**

Folder export, the review sheet, and the per-image gallery download all called bare `fetch()` on image URLs, which silently produced zero images for any adopter-mode session — `imagegen:` is a private scheme with no fetch handler. All three now obtain bytes from one `resolveImageBlob` helper that reads `imagegen:` paths through the linked folder and fetches everything else, so the documented Folder export actually lands images alongside `manifest.json`.
