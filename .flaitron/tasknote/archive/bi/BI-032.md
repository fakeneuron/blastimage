# BI-032 | approved-collision-guard

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-030.2]]

## 🎯 Goal

Stop `promoteKeeperToApproved` silently overwriting an existing `approved/` file when two rounds produce the same filename — raise a blocking confirm naming the collision, and revert the decision when the user declines.

## ✅ Acceptance

- [x] Approving an image whose filename already exists in `approved/` **with different bytes** raises a blocking confirm before any write
- [x] Accepting the confirm promotes as before (the existing file is replaced) and writes the `selection.json` approve entry
- [x] Declining the confirm writes nothing to disk **and** reverts the image's decision to its previous value, so session state and disk stay in step
- [x] Re-approving the *same* image (identical bytes already in `approved/`) passes silently — no confirm
- [x] Approving when `approved/<name>` is absent (or `approved/` itself is absent) passes silently — no confirm
- [x] Where `window.confirm` is unavailable (SSR/tests) the approve proceeds, mirroring `confirmSlugBreak` — asserted by construction: `confirmApprovedOverwrite` carries the identical `typeof window`/`typeof window.confirm` guard, and every hook test stubs `confirm` explicitly rather than relying on the fallback
- [x] `submitFeedback(action: 'approve')` runs the same guard, and a declined confirm preserves the feedback text it committed
- [x] The flat, filename-keyed `approved/` contract is unchanged — no round namespacing, no renamed files
- [x] Tests cover the FS conflict detection and the confirm/revert orchestration; `npm test`, `tsc --noEmit`, `eslint` all clean

**Discovery Notes:**

**Clarification (asked, one question, recommended option taken).** Four fixes were put to the operator: blocking confirm + revert on decline · refuse with a red banner · auto-disambiguate the filename · namespace `approved/r<N>/`. **Chosen: blocking confirm, revert on decline.** It is the sibling of the pattern `BI-030.3` already established for a destructive-but-legitimate action, it keeps the flat filename-keyed `approved/` contract documented in `docs/REVIEW-LOOP.md` §3 and `ADOPT.md` intact (auto-disambiguate and round-namespacing both break what host-repo promotion reads), and it leaves the user in control — replacing an earlier round's approval with a better one is a *reasonable* thing to want, so refusing outright would cost an extra step on the common path.

**Why the decision must revert on decline.** `handleImagegenApprove` is fired *after* `commit`, as a floating promise, from both `setImageDecision` and `submitFeedback`. So by the time the confirm is answered the session already reads `approved`. Declining without a revert would reintroduce exactly the drift this epic family exists to close — session says approved, disk holds someone else's image. The revert uses `sessionRef.current` (set synchronously by `commit`), which is the *post*-commit session, so `submitFeedback`'s feedback text survives a declined approve; only the decision field is rolled back. This is the mirror of `handleImagegenUnapprove`'s deliberate use of the *pre*-commit `session`, and for the same kind of reason — each handler needs the state that makes its own guard correct.

**Detection lives at the FS layer, not in session state.** A session-state check (`buildApprovedImages` with a matching `roundImageFilenameFromUrl`, mirroring the undo's `filenameStillUsed`) would miss the most likely real case: an approval made in an earlier browser session or by a teammate, where the file is on disk but no longer in this session's model. Detection is therefore a disk read — `approved/<name>` exists **and its bytes differ from** `rounds/r<N>/<name>`. The byte comparison is what makes a re-approve of the same image silent rather than a spurious prompt; size is compared first so the common non-collision costs one `File.size` read.

**Session state is still consulted — for the message only.** The confirm names which round the resident file came from when it can: another still-approved image in `buildApprovedImages(session)` whose `roundImageFilenameFromUrl` matches the keeper. When there is no such record (the cross-session case above), the message degrades to "promoted earlier" rather than guessing a round. Provenance is not recoverable from `approved/` itself — it is a flat directory with no manifest — and adding one is out of scope.

**Explicit assumptions.** (1) Replacing an earlier approval is legitimate when confirmed — the fix targets the *silence*, not the overwrite. (2) The r1 file is genuinely unrecoverable once replaced (`approved/` holds the only promoted copy; the r1 *round* file is untouched in `rounds/r1/`, so the confirm says the approved copy is lost, not the source). (3) `window.confirm` unavailable ⇒ proceed, matching `confirmSlugBreak`; the guard is a UX safeguard, not a correctness gate. (4) Approving while the imagegen folder is unlinked stays a no-op — `handleImagegenApprove` already returns early, and there is no disk to inspect. (5) `handleImagegenUnapprove`'s existing guards are untouched; this task adds the symmetric guard on the *approve* side.

Discovery surfaced no significant deviation → skip 🛠️.

**Implementation Notes:**

Three source files, ~70 LOC. Detection is a pure disk read (`approvedFileConflict`) that answers one question — *would promoting replace a different image?* — and returns `Result<boolean>`; policy (whether to ask, what to say, what to roll back) stays entirely in the hook, which is where every other user-facing string in this codebase lives.

Two details carry the correctness:

1. **Bytes, not existence.** A bare existence check would prompt on every re-approve of the same image. `sameBytes` compares `File.size` first, so the common non-collision costs one metadata read and never buffers an image.
2. **Rollback reads `sessionRef.current`, not `session`.** `handleImagegenApprove` is fired *after* `commit` as a floating promise, so the session already says `approved` by the time the confirm is answered. `sessionRef.current` is set synchronously by `commit`, so it is the post-commit state — reverting through it rolls back only the decision field and leaves `submitFeedback`'s freshly committed feedback text intact. This is the deliberate mirror of `handleImagegenUnapprove`, which uses the *pre*-commit `session` for its own guard; both are commented at the code.

The confirm names the resident file's round when session state still knows it (`buildApprovedImages` filtered to the same keeper filename, excluding the image being approved) and degrades to "promoted earlier" otherwise — `approved/` carries no provenance of its own.

**Final Summary:**

Approving an image no longer silently destroys an earlier approval. Because `imagegen/approved/` is flat and round images are named `<slug>-NNN.<ext>`, approving `hero-001.jpg` from r2 used to overwrite r1's file of the same name with no warning — the last unsurfaced one-way write `BI-EPIC-030` set out to close, deferred there by `BI-030.2` (which guarded only its *undo* against the same collision) and filed by the `BI-030.N` audit.

Three source files, ~70 LOC: `approvedFileConflict` (`lib/imagegenFs.ts`) compares the resident file's bytes against the round file and reports only a genuine replacement; `approvedConflict` (`lib/ImagegenContext.tsx`) carries it across the injection seam; `confirmApprovedOverwrite` + the guard in `handleImagegenApprove` (`lib/useWorkspace.ts`) ask before writing and roll the decision back on decline. Each is the mirror of an existing symbol in the same layer, so the BI-024.2 layering is unchanged and no fourth error channel was invented — the confirm is `confirmSlugBreak`'s shape, down to the SSR guard.

Two choices carry the correctness and are commented at the code, not just here: detection compares **bytes rather than existence**, so re-approving the same image stays silent instead of nagging; and the rollback reads **`sessionRef.current` (post-commit) rather than the pre-commit `session`**, so a declined approve from the feedback modal keeps the feedback text the user just typed and moves only the decision field. That is the deliberate mirror of `handleImagegenUnapprove`, which needs the pre-commit session for its own guard.
