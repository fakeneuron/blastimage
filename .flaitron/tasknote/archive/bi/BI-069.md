**Discovery Notes:**

- Phase 1→2: Discovery surfaced no significant deviation → skip 🛠️.
- Repro: `e2e/helpers.ts` flow looped on webkit, 2 workers, 300 runs → 5, 5, and 4 failures in three 300-run passes (~1.5%). Temp probe specs and `console.log` probes in the modal were used and reverted (tree was clean before this task; nothing probe-related is in the diff).
- Root cause: the modal mounts with the listing area empty (`min-h-[8rem] flex-1`), so the dialog is short and vertically centered. When the mount-time `onBrowse()` lands, the list grows and the dialog resizes, moving the **Link path** button ~108px (measured with a 1.5s-delayed browse: y 435 → 543). Playwright's click waits for a stable box, then clicks the old coordinates; when the listing arrives in that ~40ms window the click hits the dialog container instead. DOM-event probe on all 4 captured failures: `change` → `focusout` input → `focusin DIV#[Link your im…]` → `click DIV` with no submit, listing applied just before. It is a real UX defect too, not only a test artifact: a human clicking Link path as the tree loads misses the same way.
- Lead from the stub (listing resolving "resets the path field") **not reproduced**: with a 1.5s-delayed browse, typed text (`fill` and slow `pressSequentially`, chromium + webkit) was intact after the listing landed. `typed` is only written by `onChange`; `applyBrowse` never touches it.
- One earlier failure in a 90-run pass showed a different end state (Link path disabled, field empty, no `change` seen). It did not recur in the ~900 further webkit runs (DOM probes on); not explained, recorded as unexplained rather than folded into the cause above.
- Best practices: one class change in the presentational modal; no new abstraction. Suggestions row (`onSuggest`) also appears after mount and can shift the form when a nearby `imagegen/` exists; the e2e env has none, so it is not part of this fix — noted for follow-up.
- Archive skim (area `bi`, `test`, README table checked): BI-046 (picker + mount browse), BI-050 (set-state-in-effect split of `applyBrowse`), BI-068 (focus restore, where the flake was first seen), TEST-008 / TEST-012.2 (helper + webkit project). None record the layout shift or a height contract.
- Drift check: `e2e/helpers.ts:59` is now `:58` for the click and `:59` for `toBeHidden` — the PLAN line's `:59` points at the assertion that times out; PLAN row and SPEC contracts otherwise match.
- No clarifications needed (--unattended): assume pinning the list height is acceptable UX (the list scrolls, as it already does when `max-h-[80vh]` is hit).

**Final Summary:**

The link flake was a layout shift, not a state race: the picker's folder list grew when the mount-time browse landed, re-centering the dialog and moving **Link path** ~108px, so a click aimed at the old position hit the dialog container. The list now has a fixed height, and a new e2e (`e2e/imagegen-link-layout.spec.ts`) pins the button's position across the load (red without the fix, green with it). Evidence: 600/600 webkit runs of the real link helper after the fix, against ~1.5% failing before. The stub's "listing resets the path field" lead was not reproduced.
