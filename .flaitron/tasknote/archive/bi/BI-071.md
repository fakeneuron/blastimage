**Discovery Notes:**

- Phase 1→2: Discovery surfaced no significant deviation → skip 🛠️.
- Cause: `lib/useWorkspace.ts` `handleImagegenApprove` runs three awaited calls after the optimistic commit — `approvedConflict` (GET), `promoteApproved` (POST, `mkdir` + `copyFile` in `lib/imagegenServerFs.ts`), `writeSelection` (POST `/api/imagegen/selection`). The test ends on `Approved` / `Folder` visible, which the optimistic commit already shows. `removeFixture` (`fs.rmSync` recursive) then runs against a root the server is still writing into: ENOTEMPTY when `approved/` gains a file mid-removal, or the promote failing once the root is gone ("Could not promote" banner).
- Fix shape: the last call in the chain is the `selection` POST, and it runs only after the promote succeeds, so its response is a sufficient settle signal. Playwright `waitForResponse` set up before the Approve click is the smallest real seam; no app change and no fixed sleep.
- Scope: the test-level fix lives in the one spec the PLAN row names. `e2e/iterate-feedback-modal.spec.ts` only checks Approve's focus order (line 178-187) and never clicks it, so it writes nothing under the root and needs no change. No other spec clicks Approve.
- Archive skim (area `bi`, README table checked): BI-069 records the race as its filed follow-up; BI-063 added the promote-failure rollback behind the banner. Neither claims a settle contract. No prior tasknote touches `e2e/review-keyboard.spec.ts` for this.
- Drift check: PLAN row matches the code and the spec's current line numbers; no SPEC contract is touched.
- Best practices: one spec, no abstraction. A `settleApprove` helper in `e2e/helpers.ts` is not warranted with a single caller.
- No clarifications needed (--unattended): assume the response of the `selection` POST is the right "done" signal (it follows promote in the same handler).
