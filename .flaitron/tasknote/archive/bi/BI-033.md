# BI-033 | delete-slug-guard

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-030.3]]

## 🎯 Goal

Stop `deleteTask` silently severing a task from the round files, `approved/` promotions, and `selection.json` entries it owns on disk — surface the consequence before the delete applies, the way `renameSlugBreak` already does for a rename.

## ✅ Acceptance

- [x] Deleting a task that carries `imagegen:rounds/r<N>/…` images opens a modal naming the disk slug, the affected round(s), and any `approved/` copies the task promoted — replacing the generic "This cannot be undone" confirm
- [x] Deleting a task with no on-disk round images shows the same modal with the plain confirmation text only (no imagegen detail invented)
- [x] When the task promoted ≥1 file into `approved/` **and** the imagegen folder is linked, the modal offers an opt-in "also remove the approved copies" checkbox; the checkbox is absent otherwise
- [x] Confirming with the box ticked removes each `approved/<keeper>` the deleted task owned — skipping any filename another still-approved image still needs — and writes a `skip` entry into each affected round's `selection.json`
- [x] Confirming with the box unticked (or absent) removes the task from session state only; nothing is written to disk
- [x] Cancelling (button, Esc, or backdrop) leaves both the session and the disk untouched
- [x] `Sidebar` no longer owns a delete confirm — the 🗑 button routes straight to the modal
- [x] Detection is pure session state; `imagegen.linked` gates only the cleanup *offer*, never the warning (mirrors [[BI-030.3]])
- [x] Tests cover the pure predicate, the hook's retraction orchestration, the modal's checkbox gating, and the Sidebar's no-confirm path
- [x] `npm test`, `npx tsc --noEmit`, `npm run lint` all clean

**Discovery Notes:**

**What a delete actually severs (three distinct consequences, not one).** The PLAN line says "orphans its on-disk round", which is the mildest of the three:

1. **`approved/` promotions become unreachable.** If any of the task's images are `decision: 'approved'`, `handleImagegenApprove` has already copied bytes into `imagegen/approved/<keeper>` and written an `approve` entry into `selection.json`. `handleImagegenUnapprove` — the undo `BI-030.2` built — works entirely off session state (`buildApprovedImages(session)`), so deleting the task destroys the only in-app record of that promotion. The file stays in the user's repo forever with no UI path to remove it, and it silently drops out of `buildExportManifest`. This is the genuinely one-way consequence and the strongest argument for a guard.
2. **`selection.json` keeps a live instruction for a task that no longer exists.** `requestNextRound` writes an `iterate` entry keyed by slug; `handleImagegenApprove` writes an `approve` entry. Neither is retracted on delete, so the next `/blast-iterate` still acts on the deleted task's slug.
3. **`rounds/r<N>/…` files are orphaned — but recoverably.** `ingestRoundBatch` upserts by `slugify(name)` and mints a task for an unknown slug, so `↻ Load round` re-creates the deleted task from `batch.json`. What does *not* come back is per-image state (decisions, ratings, feedback) — so post-reload the session says "nothing approved" while `approved/` still holds the promoted copy. That divergence is precisely the drift `BI-EPIC-030` exists to surface.

**Detection is the same shape as `renameSlugBreak`, with one addition.** Round membership comes from the same derivation (`roundNumberFromImageUrl` over the task's image URLs, deduped and sorted). The delete case additionally wants the approved-keeper filenames, because consequence 1 is the one worth naming in the message — and those come from `buildApprovedImages(session)` filtered to the task, exactly the derivation `handleImagegenUnapprove` already uses. No new traversal, no new abstraction.

**The structural wrinkle: delete already has a confirm, and it's in the wrong layer.** `renameTask` and `handleImagegenApprove` had no pre-existing dialog, so `BI-030.3` and `BI-032` could add hook-owned confirms without touching a component. Delete is different: `Sidebar.handleDeleteTask` (`components/Sidebar.tsx:104`) already asks "Delete task '<name>'? This cannot be undone." — a legacy of `BI-003`'s native-dialog shell — and it is the *component* asking. A hook-side guard therefore has to either take that confirm over or stack a second dialog on top of it. That is a real fork in the work, so it went to the operator rather than being assumed.

**Clarifications (two asked, both answered).**

1. *Where does the join-aware warning live?* → **the hook/app owns it; `Sidebar` drops its `window.confirm`.** One dialog whose content escalates when there is a disk join, rather than a second dialog stacked on the first. Declined: keeping the Sidebar confirm and stacking a second (two dialogs on the risky path), and enriching the Sidebar's own string (which would make a component render a consequence message every other guard in this repo keeps in the hook).
2. *Warn only, or also clean up?* → **warn, and offer the cleanup as an explicit choice.** The operator was told that `window.confirm` cannot express a third option and that this therefore pulls in a real modal — materially more UI than the PLAN line implies — and chose it anyway. Declined: warn-only (the narrowest read of the filed task) and unconditional retract-on-confirm (deletes repo files as a silent side effect of a task delete).

**What answer 2 costs, stated plainly.** This is no longer a predicate-plus-confirm-string task. It adds a component (`DeleteTaskModal`), moves the delete confirm out of `Sidebar`, and gives `deleteTask` an async disk-retraction path it does not currently have. That is the scope the operator chose with the trade-off in front of them; it is recorded here so the diff's size is not a surprise on review.

**Why the modal is the right shape once cleanup is optional.** The retraction is genuinely destructive (it removes files from the user's repo) and must therefore be *opt-in and visible*, not a hidden consequence of clicking OK. A checkbox inside the same dialog that names the files keeps consent and consequence on one screen, and the repo already has the idiom — `IterateModal`/`FeedbackModal` are backdrop+Esc+Cancel dialogs driven by `Workspace.tsx` state, so no new UI pattern is invented.

**Layering under the new shape.** Detection stays pure in `lib/workspace.ts` (`deleteSlugBreak`); the *disk* work stays in the hook (`deleteTask`'s optional retraction, reusing `unpromoteApproved` + `buildSkipSelectionTask`); the modal is presentational, exactly like `IterateModal`. `Workspace.tsx` already imports from `@/lib/workspace` (`countGeneratedImageBytes`), so it derives the risk directly and `UseWorkspace` grows by nothing but `deleteTask`'s options parameter.

**Retraction must read the pre-delete session.** `buildApprovedImages` is a derivation over `session.tasks`, so once the task is gone there is nothing left to retract. The plan (which keeper filenames, which rounds) is therefore computed *before* `commit(deleteTaskFrom(...))`. This is the same class of ordering care `BI-032` documented in reverse (`handleImagegenApprove` deliberately reads the *post*-commit `sessionRef.current`): each handler needs the state that makes its own guard correct.

**Explicit assumptions.** (1) The `rounds/r<N>/…` source files are never touched — they are the terminal loop's artifacts, the app does not own them, and `↻ Load round` re-mints the task from `batch.json`, so deleting them would destroy the one recovery path. Only the `approved/` *promotions* (copies this app made) are eligible for cleanup. (2) `imagegen/tasks.json` is still not written by the app (`docs/REVIEW-LOOP.md` §2), so a deleted task reappears on the next round unless the user edits it in the host repo — the modal says so rather than pretending otherwise. (3) The cleanup offer requires `imagegen.linked`, because unlike the *warning* it needs an FS handle to do its work — the same distinction `BI-030.2` (no-op when unlinked) and `BI-030.3` (warn regardless) drew between them. (4) Cleanup failures surface through the existing `setError` banner rather than blocking the delete; the session removal has already been committed by then.

**Implementation Notes:**

Five source files, ~200 LOC (of which the modal is ~145 — the cost of answer 2). One new component, no new `ImagegenApi` method, and `UseWorkspace` grew by a single optional parameter.

Three details carry the correctness:

1. **The retraction plan is read before the commit.** `buildApprovedImages` derives from `session.tasks`, so once `deleteTaskFrom` lands there is nothing left to retract. `deleteTask` therefore computes both the plan and the orphan filter off the pre-delete `session`, then commits, then fires the async disk work. This is the deliberate mirror of `handleImagegenApprove`, which reads the *post*-commit `sessionRef.current` for its rollback — commented at both call sites.
2. **`orphanedApprovedFilenames` is BI-030.2's `filenameStillUsed` widened from one image to a whole task.** `approved/` is a flat namespace, so a filename the doomed task owns may still be needed by another task's approval; the guard filters those out before any `unpromoteApproved` call.
3. **A `skip` entry is written for every joined round, not just rounds with approvals.** `mergeRoundSelection` merges by slug and `skip` clears the entry's keeper and prompt, so one write retracts a leftover `approve` *or* `iterate` instruction — consequence 2 from Discovery, which an approvals-only sweep would have missed.

The `rounds/r<N>/` source files are never touched, by design: they are the terminal loop's artifacts, and `↻ Load round` re-minting the task from `batch.json` is the only path back from a mistaken delete. The modal says so rather than implying the delete is total.

`components/Workspace.test.tsx`'s `deleteTask: () => {}` stub needed no edit — a zero-arg function is assignable to the widened signature, and `tsc --noEmit` confirms it. Left untouched rather than churned.

**Final Summary:**

Deleting a task no longer silently severs it from the round state it owns in the host repo. Where the 🗑 button used to ask a generic "This cannot be undone", it now opens a modal naming the disk slug, the joined rounds, and the `approved/` copies the task promoted — and offers to clear the two consequences that are genuinely one-way. This is the last half-edge the `BI-030.N` audit named, and it closes the `slugify(name)` join in both directions: `BI-030.3` guarded the rename, this guards the delete.

Discovery found the PLAN line understated the problem. It described one consequence ("orphans its on-disk round"), which is the *mildest* — `ingestRoundBatch` upserts by slug, so `↻ Load round` re-mints a deleted task from `batch.json`. The two it omitted are the real ones: `approved/` copies become permanently unreachable (`buildApprovedImages` is their only record, so `BI-030.2`'s undo path dies with the task), and `selection.json` keeps instructing `/blast-iterate` for a task that no longer exists. The modal states all three and the opt-in cleanup targets exactly the first two.

Five source files, ~200 LOC. `deleteSlugBreak` (`lib/workspace.ts`) is the pure decision, beside `renameSlugBreak`; `deleteTask`'s optional retraction (`lib/useWorkspace.ts`) reuses `unpromoteApproved` + `buildSkipSelectionTask`, so `ImagegenApi` gained **no new method**; `DeleteTaskModal.tsx` is a new component on the `IterateModal` idiom; `Sidebar.tsx` lost its `window.confirm` and `Workspace.tsx` owns the modal state. One structural decision was the operator's, taken with the trade-off stated: offering the cleanup as a *choice* rather than warn-only or always-clean is what pulled in a real modal (`window.confirm` cannot carry a third option) and moved the delete confirm out of `Sidebar`. That is ~145 of the 200 LOC. The narrower alternatives were surfaced and declined at the 🛠️ gate.
