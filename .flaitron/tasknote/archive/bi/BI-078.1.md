**New findings the starter did not have.**

- **Safari and HTTP Range.** `resolveDisplayUrl` returns a direct `/api/imagegen/file` URL (BI-045 removed the blob cache; `retainDisplayUrl` is a no-op). A `<video>` element would therefore fetch the route itself. The route reads the whole file and answers 200 with no `Accept-Ranges`. Safari generally requires byte-range (206) responses to play `<video>`, and webkit is a required e2e project (TEST-012.2). Adding the MIME type alone is unlikely to be enough. Unverified until a child tests it in webkit.
- **`nosniff` needs a real MP4 fixture.** TEST-007.3 found that a fixture whose bytes do not match its extension will not render. The video fixture must be a genuine small H.264 file. `ffmpeg` and `ffprobe` are installed locally (`/opt/homebrew/bin`).
- **Playwright codec support is unverified.** `@playwright/test` is 1.63.0. Whether its bundled Chromium decodes H.264 is not checked. The e2e child should assert on DOM, attributes, and exported bytes, and treat decode as a webkit-side check until proven.
- **Iterate has no meaning for a clip today.** `/blast-iterate` passes the keeper to `image_edit` as the reference. An `.mp4` keeper cannot seed that. A clip round needs its own iterate rule.
- **The existing `ref` field can carry the source still.** `RoundBatchTask.ref` is "a path relative to `imagegen/`", so `ref: "approved/<slug>-NNN.<ext>"` names the still with no new field. Media kind can be derived from the filename extension, which avoids a persisted discriminator and a `SCHEMA_VERSION` bump.
- **This repo has no `imagegen/` folder and no ignore rule for one.** blastimage's own promo still (`brand/promo-16x9.webp`) is 1600×900, 16:9.
