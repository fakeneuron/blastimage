**Rule behavior measured, not assumed.** The PLAN line predicts the fix means "`key`-prop or derive-during-render rewrites with real regression risk". Before touching any real file I ran a throwaway probe (`components/__probe.tsx`, deleted) through `npx eslint` to establish what `eslint-plugin-react-hooks@7.1.1` actually accepts. Five shapes, and the results reshaped the plan:

| Probe | Shape | Verdict |
|---|---|---|
| A | Derive-during-render reset (`if (prev !== src) { setPrev(src); setDisplaySrc(src); }`) in a component | **clean** |
| F | The same guarded adjustment inside a **custom hook** | **clean** |
| B | `setState` after an `await` inside the effect's own async IIFE | **clean** |
| G / H | A `useCallback` (or an injected setter) invoked **after** an `await` inside that IIFE | **clean** |
| C | A `useCallback` invoked **synchronously** from the effect body — even when its own first statement is an `await` | **flagged** |
| D | Ref write inside an effect | **clean** |

Two findings do the real work here. First, `set-state-in-render` does **not** fire on the React-documented "adjusting state when a prop changes" pattern, so sites 1, 2 and 4 have a rule-clean shape that needs no `key` prop and no component split — which is what the PLAN line feared. Second (probe C vs. G), the rule's model is *reachability from a synchronous call in the effect body*, not "is there an await somewhere": moving the `await` inside `navigate` would not have helped site 3, and only restructuring the effect itself does.

**Sites 1, 2, 4 — the same shape, three times.** All three are "reset some state when an input changes", which the probe showed `react-hooks@7` accepts as a guarded render-time adjustment. Each keeps a companion state holding the input the current value was derived *for*:

- `components/ResolvedImage.tsx` — `resetFor !== src` → drop to the raw `src`. Still keyed on `src` alone, so BI-042.2's property (a `blobEpoch` bump must not flash mounted images back to their raw URL) is untouched. The reset now lands **before paint** rather than one committed render later, which is strictly tighter than the effect it replaces.
- `components/TaskDetail.tsx` — `draftFor !== task?.id` → resync the draft. The guard *is* the BI-007 invariant made explicit: it compares task **identity**, so an external `basePrompt` rewrite under an unchanged task cannot clobber an in-progress edit. The `useEffect` import and the `exhaustive-deps` disable on the old dep array both went with the effect — orphaned by this change, not adjacent cleanup.
- `lib/useWorkspace.ts` — `!imagegen.linked && availableRounds.length > 0` → clear. Two lines inside the existing hook; BI-049's decision to leave the file whole is respected, and BI-042.4's explicit instruction not to touch the discover effect's `[imagegen, imagegen.linked]` deps is honoured (only the `!linked` branch moved out; the deps are byte-identical). The `length > 0` guard is what keeps it to the single render where the link actually drops.

**Site 3 was the only genuine restructure**, because probe C ruled out the cheap fix: the rule bans setState *reachable synchronously from an effect body*, so pushing the `await` inside `navigate` would not have helped — the effect simply cannot call it. Split the browse-result tail into `applyBrowse`, which `navigate` and the mount effect now share; the effect starts the browse synchronously (`onBrowse()` sets no state) and applies it in its own continuation. Parallelism with the suggestions fetch is preserved, and the four-line tail is single-sourced rather than duplicated.

**One assumption withdrawn mid-execution.** Discovery assumption 3 accepted initialising `busy` to `true` (the mount fetch *is* in flight on first paint) and judged the only cost to be a frame of disabled controls. That was wrong, and lint/typecheck/tests would all have passed with it in: `useFocusTrap` selects the first **enabled** focusable at mount (`FOCUSABLE` excludes `[disabled]`, and its effect is mount-only), so disabling the path field moves opening focus onto Cancel — a keyboard-behavior change in the modal BI-039 engineered. Reverted to `useState(false)`; the mount load deliberately does not raise `busy`, which also removes a latent wart in the original, where focus landed on the path input and was then blurred as `setBusy(true)` disabled it a commit later. Nothing the mount fetch feeds is on screen yet anyway, so the type-a-path fallback stays usable while the tree loads. The reasoning is recorded at the site.

**Site 5** — `Capture`'s ref write moved into an effect (`[api, apiRef]`). Safe because every caller drains effects with `act` before reading `apiRef.current`; both tests that use it pass unchanged.

**Refactors made:** only `applyBrowse`, and only because leaving it out would have duplicated the browse tail four lines from itself on the touched path. **Deferred:** the three remaining `react-hooks/exhaustive-deps` disables (`ImagegenLinkModal`, `useWorkspace`, `useFocusTrap`) — react-hooks@5-era suppressions that DEPLOY-002 did not add and this PLAN line does not name.
