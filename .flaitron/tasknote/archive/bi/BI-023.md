**Discovery Notes:**

**The wall (unchanged from BI-022.5, reconfirmed).** blastimage's whole generation model is the Grok Build sandbox: `lib/generate.ts` delegates to an agent-installed `globalThis.__grokImagineProvider` that calls `image_gen` and reads results off the filesystem (`node:fs`). A deployed user browser on Cloudflare Pages has none of that — no agent, no `image_gen` built-in, no filesystem. BI-013 gap #2 already proved there is no transparent client-side Grok global in the page. So the deployed hosted Generate throws (caught → non-fatal "Generation failed" toast).

**What changed since BI-022.5 — the xAI public image API (the research half).** xAI now exposes image generation publicly via the xAI API platform (auth = xAI API key):
- **`grok-2-image`** (`/v1/images/generations`, OpenAI-compatible) — $0.07/image, up to 10 variations/request, returns JPG URLs/data.
- **Grok Imagine API** (announced 2026-01-28) — `grok-imagine-image-quality` (the `-pro` model deprecates 2026-05-15); supports **batch generation, aspect-ratio control, and image-to-image editing** — which maps almost 1:1 onto blastimage's `batchSize` + `3:2` aspect + `referenceImages` flow. So a drop-in xAI-API provider for the existing seam is genuinely feasible.

**The collision (why "possible" ≠ "should build now").** Calling that API needs an API key somewhere. The hosted deploy is a **static export** (no server/edge — `docs/DEPLOY.md`). Three key-delivery shapes, each with a cost:
- *Browser-side key (BYO):* user pastes their xAI key → localStorage → browser fetches `api.x.ai` directly. Serverless-compatible, but the key is visible in browser/devtools/network, and per-user billing. **User ruled this out** (local-only stance; matches BI-022.1 operator-key non-goal extended to user-key).
- *Server/edge proxy:* a Cloudflare Worker/Pages Function holds the key as a secret; browser → `/api/generate` → xAI. Hides the key but **adds a backend** to a deliberately-static deploy — new infra to build, secure, and fund.
- *Local-only (status quo):* generation stays in Grok Build; hosted mode is review/persist/import. The **session importer (BI-022.7)** already makes "generate locally → export → import into hosted for review/share" a complete loop. **This is the user's chosen direction.**

**Recommendation: defer the hosted-generation build.** Keep generation local; hosted = review/persist/import. The doc records the xAI Imagine API as the concrete path *if* the decision ever flips, so a future task (e.g. a BYO-key or edge-proxy build) starts from this analysis rather than re-spiking.
