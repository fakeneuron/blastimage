# BI-030.2 | reversible-approve

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[BI-EPIC-030]]

## 🎯 Goal

Make clearing an `approved` decision reversible — removing the image from `imagegen/approved/` and rewriting its `selection.json` entry — so a mis-click no longer requires manual cleanup of the user's repo.

## ✅ Acceptance

- [x] Clearing an `approved` decision (toggle-off to `undecided`, or switching to `kept`/`discarded`) deletes the keeper from `imagegen/approved/`
- [x] The same clear rewrites the task's `selection.json` entry to `{ slug, decision: 'skip' }` via the existing upsert-by-slug merge
- [x] Clearing one approval does not clobber a sibling approval: the `selection.json` entry is only rewritten when no other image of that task is still approved in that round, and the file is only deleted when no other still-approved image maps to the same `approved/` filename
- [x] Deleting an already-absent `approved/` file (or an absent `approved/` dir) succeeds — the clear is idempotent
- [x] Clearing an approval while the imagegen folder is unlinked is a silent no-op (symmetric with the approve path)
- [x] `submitFeedback(action: 'keep')` on a previously-approved image runs the same clear
- [x] Tests cover the FS delete path and the clear/guard orchestration; `npm test`, `tsc --noEmit`, `eslint` all clean

**Discovery Notes:**

**Clarifications (both answered, recommended option taken):**

1. *Cleared entry shape in `selection.json`* → **rewrite to `{ slug, decision: 'skip' }`**, not entry removal. `skip` is the documented "leave the task untouched this round" value (`docs/REVIEW-LOOP.md` §3), and it flows through the existing upsert-by-slug `mergeRoundSelection` unchanged — removal would need new merge semantics. `planIterateTasks` already ignores non-`iterate` entries and `planRefBootstrapCopies` requires a keeper, so a keeper-less `skip` entry is inert for `/blast-iterate`.
2. *Unlinked folder* → **silent no-op**, mirroring `handleImagegenApprove`'s `if (!session || !imagegen.linked) return`. Approve itself no-ops when unlinked, so in a same-session flow there is nothing on disk to clean; a warning would fire spuriously. Accepted limitation: an approval made in an earlier *linked* session and cleared in a later *unlinked* one still leaves the file behind, and the two cases are indistinguishable from session state.

**Sibling-approval hazard (found in Discovery, guarded in scope).** Nothing enforces one approved image per task, but `selection.json` holds one entry per slug and `approved/` is a flat filename namespace. So a naive clear introduces two *new* silent-drift bugs it would be wrong to ship:

- clearing image A of task `hero` would rewrite the slug entry to `skip`, clobbering a still-approved image B of the same task;
- `approved/` is keyed by bare filename, so `r1/hero-001.jpg` and `r2/hero-001.jpg` collide there — deleting for one round could remove the file a still-approved image of another round depends on.

Both are guarded with one `.some()` each over `buildApprovedImages(session)` minus the cleared `imageId` (the pre-commit session is used deliberately, so the excluded id yields exactly the post-commit approved set). This reuses an existing derivation; no new helper.

**Explicit assumptions:** (1) the `approved/` filename-collision hazard itself is pre-existing and stays out of scope — this task only avoids *worsening* it; (2) deletion is idempotent (missing file or missing `approved/` dir both return ok) so a repeated clear is safe; (3) `submitFeedback(action: 'save')` does not change the decision and therefore never triggers a clear.

Discovery surfaced no significant deviation → skip 🛠️.

**Implementation Notes:**

Five files, ~90 LOC of source. `removeApprovedFile` is idempotent by design: a missing `approved/` dir and a `NotFoundError` from `removeEntry` both return ok, so a repeated clear (or a clear of an approval made before the folder was linked) is safe rather than an error the user has to read. `handleImagegenUnapprove` deliberately reads the *pre-commit* `session` and excludes `imageId`, which yields exactly the post-commit approved set — that is what makes both guards correct without threading extra state.

`setImageDecision` and `submitFeedback` capture the previous decision before `commit`, then fire the clear when it was `approved`. `submitFeedback(action: 'save')` leaves the decision untouched and therefore never clears.
